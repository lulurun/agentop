# Setup

agentop is a service plus an app. Each machine that runs agents runs the service, and
the app connects to any service it can reach. The app is served by the service
at `/` (it was at `/app/` until 2026-11-14, which now redirects there).

## On a machine of your own

Needs Python 3.13+, tmux, and Node 20.19+ or 22.12+ to build the app.

```bash
git clone <repo> agentop && cd agentop
pip install -e .
(cd ui && npm ci && npm run build)   # the build output is not committed
agentop serve                        # http://127.0.0.1:9775
agentop open                         # opens the app, signed in
```

As it starts, `agentop serve` checks the host:

- It looks for each agent tool's program (`claude`, `codex`, `agy`) on the PATH of the user's login shell, where sessions run, and on its own. It refuses to start when it finds none. The New session dialog offers only the tools it found; restart the service after installing another.
- It installs or updates agentop's skills ([src/agentop/skills/](../src/agentop/skills/README.md)) for each tool found that takes them: Claude Code in `~/.claude/skills/`, and Codex in `~/.codex/skills/`.

## A devhost, behind a proxy host

The service binds `127.0.0.1:9775`. An SSH tunnel forwards it to `proxy-host:7775`,
and nginx there serves it at `http://proxy-host:7700/agentop/`.

The proxy has no authentication, and plain HTTP carries the service token where a
network observer could read it. This is accepted for now: see plan section 9.1. The app
still opens there, but Connect to a service refuses that address: add the HTTPS one below.

A separate ops repo owns this setup: the `agentop-api` systemd unit that runs `agentop serve`
(linked into `~/.config/systemd/user/`), the
tunnel, and the nginx config. agentop itself only needs `agentop serve`.

**nginx must forward WebSockets.** The session list and the terminal both use them.
The config is generated by the ops repo's tunnel setup script, which sets
`Upgrade` and `Connection` for grafana and agentop. Without them the app connects
and then says the service can't open a live connection.

To deploy, use Update in the app's service status, or from the main checkout:

```bash
(cd ui && npm ci && npm run build)
systemctl --user restart agentop-api
```

Restarting leaves tmux sessions running.

Monitors check the service at `GET /api/v2/health`, which needs no token.

Print the address to paste into Connect to a service:

```bash
agentop service connect-info --url https://agentop.example.com
```

### HTTPS

The devhost is also at `https://agentop.example.com`, which is the address to
use. The ops repo's HTTPS setup script installs it as its own nginx site with a
Let's Encrypt certificate, and `certbot.timer` renews it. To remove the site, delete
its file in `/etc/nginx/sites-enabled/` on proxy-host and reload nginx.

It uses port 443, not 7700: nginx can't mix TLS and plain HTTP on one port, and the
other apps on 7700 are plain HTTP.

### On a phone

The app is installable: open `https://agentop.example.com` and use Add to Home Screen
(Safari's Share menu on iOS; the menu's Install app or Add to Home screen in Chrome on
Android). It then opens full screen with its own icon. A phone installs only from an
HTTPS address, so not from a plain `http://` one on the LAN. The manifest is in
`ui/public/`; the icons are made from `assets/logo/agentop.svg` by the build.

## Connecting from the app

Load the app from your own machine's service, `http://127.0.0.1:9775/`, then use
Connect to a service in the service menu. A browser allows a loopback page to reach other
addresses. A page loaded from the proxy can use only the proxy: it can't reach your
machine's loopback.

## Controlling a service

```bash
agentop service status
agentop service stop       # or restart. Sessions keep running
agentop service update     # pull, install, build, restart; goes back if that fails
```

The same actions are in the app, in each service's Status. The CLI and the app both
ask the running service, which knows whether systemd runs it or it was started with
`agentop serve`, and acts on itself. Started by hand, restart runs it again in the same
terminal.

Nothing starts a stopped service, since it isn't there to answer. Start it on its
machine with `agentop serve`, or with the system service that runs it. Until then the
app shows a red dot and says so.

`update` needs a clean checkout on `main` that can reach its git remote, not
systemd. It writes
progress to `~/.agentop/state/update-status.json` and detail to `~/.agentop/logs/update.log`.
If the new version fails to install or start, it resets to the previous commit and
says so, and the failed commit stays on the remote until it is fixed. If a service
started by hand died starting the new version, the update starts it again in the
background, logging to `serve.log`.

## Desktop app

On a PC, the desktop app runs this computer's service for you. It needs agentop
installed as above (the app runs the `agentop` on your login shell's `PATH`, or
`AGENTOP_BIN`), but no `agentop serve` and no systemd unit.

- **Open it**: it starts `agentop serve` on `127.0.0.1` (port 9775, or `port` from
  `config.toml`) and opens signed in. If a service already answers there, such as a
  systemd unit, it uses that one instead.
- **Close it**: it stops the service it started. Sessions keep running in tmux and
  are there the next time. A service it didn't start keeps running.
- The service's output goes to `~/.agentop/logs/desktop-serve.log`. If it doesn't
  start, the app says why.

**Linux.** Download `agentop-desktop_<version>_amd64.AppImage` from the newest `agentop-desktop`
release on GitHub, then:

```bash
chmod +x agentop-desktop_*_amd64.AppImage
./agentop-desktop_*_amd64.AppImage            # needs fuse2 (Arch: pacman -S fuse2), or add --appimage-extract-and-run
```

Each start writes `~/.local/share/applications/agentop-desktop.desktop` and its icon
(`~/.local/share/icons/hicolor/512x512/apps/agentop-desktop.png`), launching the copy
last opened. On Wayland the taskbar takes the icon only from that entry, and shows a
generic one without it. So it also puts agentop-desktop in the app launcher.

**macOS.** Download `agentop-desktop.app` from the same release. It isn't signed yet, so open
it the first time with right-click, Open.

**Updates.** When a newer `agentop-desktop` release is out, the header shows **App update**.
Clicking it installs the update and restarts the app; sessions keep running. A copy
built by hand can't replace itself, so there the button opens the release page.

**Building it yourself** needs Rust and the WebKitGTK 4.1 development files. On Arch
those are `webkit2gtk-4.1`, `gtk3`, `libsoup3`, and `librsvg`.

```bash
scripts/build-app.sh             # the UI, then the app: desktop/src-tauri/target/release/agentop-desktop
scripts/build-app.sh --appimage  # also an AppImage in desktop/src-tauri/target/release/bundle/appimage/
```

The app shows the UI that this computer's service serves, so `scripts/build-ui.sh` on
its own is enough to change what the app shows: reload the window afterwards.

The app keeps tokens for other services in the OS keychain. Where there is none, such as
Linux with no secret service running, it keeps them in `~/.agentop/state/desktop-tokens.json`
(mode 0600), next to `service.json`, which holds the service token in plain text anyway.

## Building and releasing

| Script | Does |
|--------|------|
| `scripts/build-ui.sh [--clean]` | Builds the web UI into `src/agentop/service/webdist/`, which the service serves. `--clean` reinstalls `node_modules` |
| `scripts/build-app.sh [--appimage]` | `build-ui.sh`, then the desktop app |
| `scripts/release.sh 1.2.0` | Releases agentop as `v1.2.0`: sets the version in `pyproject.toml`, `tauri.conf.json` and `Cargo.toml`, commits, tags, and pushes after asking. The `desktop` workflow builds, signs, and publishes the release `agentop-desktop v1.2.0`, and installed apps offer the update |

The script runs only on `main`, clean and level with `origin/main`, and builds the UI
and the app first, so nothing is tagged that doesn't build. The tag is also what
services set to `update_from = "release"` update to; others follow `main`.

The `desktop` workflow needs the repository secret `TAURI_SIGNING_PRIVATE_KEY`, the
private half of the updater key whose public half is in `tauri.conf.json`.

## Exposing a service

`agentop serve` binds `127.0.0.1` unless told otherwise, and that is the safe
default. Everything under `/api/v2` except `/health` needs a client's token, which
the service token signs in. But tokens are all there is: whoever holds the service
token, or a live client token, can type into every agent on the machine, including
agents started with skip-permissions flags. See [Secure setup](../README.md#secure-setup). So, to reach a service from
another machine, in order of preference:

1. **An SSH tunnel.** `ssh -L 9775:127.0.0.1:9775 host`, then use
   `http://127.0.0.1:9775` locally. Nothing new is exposed, and the browser treats
   the tunnel as a loopback address.
2. **An HTTPS proxy** in front of the loopback service, as on the devhost
   (`https://agentop.example.com`). The proxy must forward WebSockets (the
   `Upgrade` and `Connection` headers). The app works under a path prefix too
   (`/agentop/`), since it uses relative addresses. Consider an IP allow-list or a
   second factor at the proxy: the token is the only thing in front of the agents.
3. **TLS in the service itself**: set `host`, `tls_cert` and `tls_key` in
   `~/.agentop/config.toml` (or `--host`, `--tls-cert`, `--tls-key`).

Plain HTTP on a non-loopback address is refused (design D6, since 2026-11-14): `agentop
serve` exits with an error when `host` isn't loopback and TLS isn't set, and Connect
to a service won't test or add a plain `http://` address that isn't loopback. Anyone
on the network path could otherwise read the token as it is sent, and every keystroke
and screen of every terminal. Connections saved before then still work, labelled "Not
encrypted". The README has a short guide to the SSH tunnel.
