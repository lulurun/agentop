# CLI Reference

All commands are accessed via `agentop <command>`. Run `agentop --help` or `agentop <command> --help` for options.

## 1 Session commands

### 1.1 list

Show all running agent sessions detected on this machine.

```bash
agentop list
agentop list --json
```

Columns: SESSION (`<project>/<name>` for agentop's), TOOL, STATUS, PID, RUNTIME, MEM, TOKENS, CWD

`--json` outputs the full session array. Useful fields:

| Field | Description |
|-------|-------------|
| `name` | Unique session identifier (also the tmux session name) |
| `project`, `display_name` | For a managed session: its project, and its name there, unique in the project |
| `readonly` | Set by the plugin that started it, such as a dialogue's agents: it takes no prompts |
| `tool` | `claude` \| `codex` \| `antigravity` |
| `managed` | `true` if started by agentop; only managed sessions can be stopped or sent prompts |
| `pid` | Agent process PID |
| `runtime_seconds` | Seconds since process started |
| `memory_mb` | Resident memory in MB |
| `token_usage` | `{input_tokens, output_tokens, cache_creation_input_tokens, cache_read_input_tokens}` |
| `ai_title` | AI-generated conversation title |
| `session_id` | Internal session ID used to resume later |
| `tmux` | `{session, window, pane}` |
| `bridge_url` | claude.ai remote-control URL (Claude, `default` project only) |

### 1.2 start

Launch a new agent session in a managed tmux session.

```bash
agentop start <session_name> --tool <tool> [--cwd <path>] [--project <name>] [--model "<model>"] [--prompt "<task>"] [--no-remote-control]
```

- `session_name` — under 32 characters, unique among the project's sessions; the tmux session is named `{session_name}-{random}`, and keeps that name for life
- `--project` — the project it belongs to (default: the project of the session this runs in, else `default`). A session working outside the project's folder gets the folder as another directory to work in (`--add-dir`, Claude and Codex)
- `--prompt` — its first prompt, typed in once the tool is up. In a project other than `default`, a session other than the Coordinator gets a first line about its project: its folder, and how to reach the Coordinator
- `--tool` — `claude`, `codex`, or `antigravity`
- `--cwd` — working directory (default: home directory)
- `--model` — its model (default: the tool's own), by name or ID, ignoring case. Claude: `"Haiku 5.5"`, `"Sonnet 5.5"`, `"Opus 5.5"`; codex: `"GPT-6-Luna"`, `"GPT-6.1-Terra"`, `"GPT-6.2-Sol"`; antigravity: `"Gemini 3.8 Flash (Low)"`, `"Gemini 3.8 Flash (High)"`, `"Claude Opus 4.6 (Thinking)"`. Any other model is an error. The list, with each model's tier, is the catalogue in [0_04_start.md 4](0_04_start.md#4-the-chooser)
- `--prompt -` reads the prompt from stdin
- From a Projects project's Coordinator it is refused: delegated work goes through `agentop coordinator task start` (section 2c). `--untracked` starts a session that is not a task, and `agentop coordinator review` counts it
- `--no-remote-control` — for Claude, do not expose the session through claude.ai remote control; tmux and agentop access still work normally

After starting:

```bash
tmux attach-session -t <session_name>-<random>
```

### 1.3 stop

Gracefully stop a managed session.

```bash
agentop stop <session> [--project <name>]
```

The session is looked up as `agentop send` does.

Sends `/exit` to the agent, waits 3 seconds, then kills the tmux session. Only managed sessions (started by agentop) can be stopped.

### 1.4 send

Type a prompt into another live session and submit it, as if the user had typed it there.

```bash
agentop send <target> "<prompt>"
agentop send <target> < prompt.txt     # no prompt, or -: read it from stdin
```

- `target` — a session's name in the sender's project (from inside a session; else `default`, or `--project`), ignoring case: `dev`. Another project's is `<project>/<name>`. The tmux name also works (`Deploy-2953204`, or `deploy` without the suffix within the project). With no match it says `I don't see an active session called 'deploy' in default`, and with several it lists them. It never starts a session
- Run from inside tmux, the prompt gets a first line `[agentop send from <project>/<name>]`; `--no-header` leaves it off
- Only managed sessions (started by agentop) take prompts, and not read-only ones, such as a dialogue's agents
- If the paste fails, it says so and presses no Enter
- It goes through the service (`POST /api/v2/send`), where prompts into one session queue, the Input bar's included, so one never lands between another's paste and its Enter. With no service answering, it types the prompt itself
- Nothing comes back by itself: switch to the target to follow it and answer it. A prompt can ask the target to reply with its own `agentop send`, which arrives as a new prompt in the sender

The `handoff` skill uses it to pass a side task, such as a deploy, from one session to another. When the sender needs a result, such as a build version, the prompt asks for a one-line reply.

### 1.5 history

Show saved/historical sessions that can be resumed.

```bash
agentop history
agentop history --tool claude
agentop history --limit 20             # default 50
agentop history --json
```

Active sessions are excluded. Columns: TOOL, TITLE, LAST ACTIVE, CWD.

### 1.6 recall

Search every past conversation on this machine: the prompts and replies the Memory plugin keeps ([0_12_03_memory.md](0_12_03_memory.md)). It reads `~/.agentop/plugins/memory/messages.sqlite` directly, so the service needn't be running. The command is the Memory plugin's: with the plugin disabled, it says so and does nothing.

```bash
agentop recall atama link                      # messages holding every word
agentop recall "atama plus" --since 6w         # a phrase; since 12h, 30d, 6w, or a date
agentop recall stores.jp --tool codex --project ~/workspace/Hotaka
agentop recall --session <session>             # its summary, then the whole session
agentop recall --session <session> --around <#id> [--radius 6]   # read around a hit
agentop recall <words> --json                  # {"sessions": [...], "messages": [...]}
agentop recall --missed "what was wanted" [--wrong]   # note a miss: nothing found, or the wrong thing
```

Words match anywhere in a message, ignoring case (an FTS5 trigram index), so part of a name, a domain, or Japanese text works. Words under three characters are matched as plain text. Results are best match first, each with its `#id`, date, tool, project, session, and, for a reply, the prompt it answered.

Above the messages, **Sessions about this** lists up to five sessions whose summary matches: its title, a few sentences, and the keywords that matched. The summaries are the Memory plugin's ([0_12_03_memory.md 5](0_12_03_memory.md#5-session-summaries)), so they find a session by what it was about even when no message has the words. A session gets one once it has been quiet for 30 minutes. The `recall` skill (`src/agentop/skills/recall/`) teaches a Claude session to use it.

Each search is noted in `~/.agentop/plugins/memory/recall.jsonl`, with how many messages and sessions it found. `--missed` notes a miss there: what was looked for, `--wrong` when something was found but not the right thing, and the searches made from the command line in the 30 minutes before. The skill notes one at the end of a recall that failed. Misses decide whether keyword search needs embeddings beside it ([0_12_03_memory.md 9](0_12_03_memory.md#9-how-other-agents-remember-and-whether-keyword-search-is-enough)); the Memory feature and Status show the count.

### 1.7 email-code

Check the Email code plugin's settings, `~/.agentop/plugins/email-code/config.toml`, by sending a test mail to the address sign-in codes go to. The command is the plugin's: with the plugin off (it is off until you turn it on), it says so and does nothing. The settings are in [0_12_00_plugins.md](0_12_00_plugins.md#email-code-email-code).

```bash
agentop email-code test
```

## 2 Dialogue commands

All dialogue subcommands are under `agentop dialogue`. The command comes from the Dialogues plugin: while the plugin is off, `agentop dialogue` says so and does nothing.

### 2.1 dialogue start

Start a two-agent dialogue on a shared topic.

```bash
agentop dialogue start \
  --brief <path/to/brief.md> \
  [--agent-a <tool>] \
  [--agent-b <tool>] \
  [--scenario <path/to/scenario.toml>] \
  [--max-turns N]
```

| Option | Default | Description |
|--------|---------|-------------|
| `--brief` | required | Markdown file describing the task/goal |
| `--agent-a` | `claude` | Tool for agent A |
| `--agent-b` | `claude` | Tool for agent B |
| `--scenario` | built-in `implementation-requirements` | Path to a scenario TOML file |
| `--max-turns` | the scenario's, or 20 | Maximum relay turns |

Both agents always run with cwd set to the dialogue's own directory at
`~/.agentop/projects/<scenario>_<brief>_<id>/` — there is no way to override this. Any
`deliverables/` folder a scenario asks the agents to create ends up there,
alongside `brief.md`, `scenario.toml`, and `dialogue.log`. Agents can still
read or write files elsewhere by using absolute paths.

Example:

```bash
agentop dialogue start \
  --agent-a codex \
  --agent-b codex \
  --brief briefs/investment-plan.md \
  --scenario src/agentop/plugins/dialogue/scenarios/shelf/strategist-challenger.toml
```

### 2.2 dialogue list

List all dialogues and their status.

```bash
agentop dialogue list
```

Columns: ID, STATUS, AGENT A, AGENT B, SESSION A, SESSION B. Sessions marked `[open]` still have a live tmux session.

Status values: `starting`, `running`, `stopped`, `completed`, `error`, `agent_missing_delimiter`

### 2.3 dialogue stop

Stop a running dialogue orchestrator and close both agent tmux sessions.
Everything said so far is already in `dialogue.log`, so the sessions are
safe to drop — the same cleanup happens automatically when a dialogue
completes on its own.

```bash
agentop dialogue stop <id>
```

### 2.4 dialogue remove

Remove dialogue data from disk.

```bash
# Remove all stopped dialogues (default, with confirmation)
agentop dialogue remove

# Remove all completed dialogues
agentop dialogue remove --status completed

# Remove a specific dialogue by ID (any status, no confirmation)
agentop dialogue remove --id <id>

# Skip confirmation prompt
agentop dialogue remove --status stopped --yes
```

`--status` bulk removal only accepts `stopped` or `completed`. Any other status requires `--id`.

If the dialogue has open tmux sessions (e.g. status is `running`), they are stopped and closed automatically before the directory is deleted.

agentop project list [--json]          # every project: owner, live sessions, folder

## 2c Coordinator commands (Projects plugin)

What they check, and why, is in [0_13_projects.md 4.3](0_13_projects.md#43-pursuit-tools-projects-plugin). Each takes `--project` (default: this session's project).

```bash
# The direction and the plan: track/<N>/DIRECTION.md, PLAN.md
agentop coordinator direction new --text - [--copy-plan] [--keep-open]   # track/<N+1>/; refused while tasks of N are open, unless --keep-open
agentop coordinator direction show
agentop coordinator plan show [--all]                          # open milestones in full, closed ones as a line and summary
agentop coordinator plan milestone add "<title>" [--before M3]
agentop coordinator plan action add M2 "<title>" [--before M2A3]
agentop coordinator plan action set M2A3 --status <planned|in progress|blocked|done|dropped> [--reason "…"] [--note "…"]
agentop coordinator plan ask [M2A4|M2] --question "…" --recommend "…" --default "…"   # a waiting-on-owner action
agentop coordinator plan answer M2A4 "<the owner's answer>"   # closes it, with the answer under it and in EXECUTION
agentop coordinator milestone close M1 --summary -             # every action done or dropped; the summary goes into PLAN.md
agentop coordinator note M2A1 "<what was done>" [--by owner]   # an execution entry without a task

# The Coordinator delegates (a task's ID is P<N>_M<m>A<a>-<k>; the commands take it or the session's name)
agentop coordinator task start --action M1A2 <name> --tool <tool> --cwd <dir> [--model "Sonnet 5.5"] [--no-remote-control] \
  --goal "<one outcome>" --accept "<criterion>" [--accept …] --artifact <file in the project> [--prompt "<more>" | --prompt -]
agentop coordinator task accept <name|id> --checked "<what you verified>" [--keep]   # stops the session unless --keep
agentop coordinator task reject <name|id> --feedback "<what to change>"             # the next round; at most 3 in all
agentop coordinator task fail <name|id> --note "<what is missing, what next>" [--keep]
agentop coordinator task list [--all] [--json]                 # each open task with its feed state and age, e.g. feed input 4m
agentop coordinator task show <name|id>
agentop coordinator task carry P1_M2A3-1 --to M1A4            # after direction new --keep-open: re-home an open task

# The task's session reports
agentop coordinator task report "<what you did, and the evidence>" [--blocked]

# The Coordinator ends a turn
agentop coordinator yield done --evidence "…" --next "…"
agentop coordinator yield waiting --next "…"           # --next: what it does next and why, kept in track/<N>/NEXT.md
agentop coordinator yield owner --question "…" --recommend "…" --default "…" [--meanwhile "…"] [--next "…"]   # also a plan ask
agentop coordinator yield blocked --need "…" --tried "…" [--next "…"]
# After done, waiting or owner, the next task report clears its context first when that is safe (0_13 section 4.3);
# --keep stops that, and --clear asks for a clear once the turn has ended, then a prompt to carry on

# Where things are: the resume view, with the yield checks as warnings
agentop coordinator status

# The Coordinator, at a milestone (or the owner, any time)
agentop coordinator review [--all] [--no-write]    # writes reviews/<time>.md and prints it
```

## 3 Service commands

```bash
agentop serve [--host H] [--port P] [--name N] [--tls-cert F --tls-key F] [--update-from main|release]   # foreground, http://127.0.0.1:9775
                                      # a non-loopback --host needs --tls-cert and --tls-key
agentop open                          # open the app in a browser, signed in
agentop service status                # whether the service runs, and how
agentop service restart               # or stop; sessions keep running
agentop service update                # pull, install, build, restart; goes back if that fails (follows the service's update_from)
agentop service token [--rotate [--revoke-clients]]   # print, or replace, the service token
agentop service clients [--revoke ID | --revoke-all]  # list the clients signed in, or sign them out
agentop service connect-info [--host H | --url URL]   # what to paste into Connect to a service
```

The service serves the app at `/` and the API at `/api/v2`. Settings in `~/.agentop/config.toml` (`host`, `port`, `name`, `tls_cert`, `tls_key`) are the defaults for `serve`. `client_ttl` (default `"12h"`) is how long a client stays signed in without renewing, at least `60s`, and `client_max_age` (default `"30d"`, `"none"` for no limit) is how long it stays signed in at most. Both take seconds, or `30m`, `12h`, `30d`. `history_window` (default `"30d"`) is how recently a past session must have been used for the app's History to list it, and `max_active_sessions` (default `20`) is how many sessions agentop starts may be active at once. `update_from` (default `"main"`) is what Update follows: `"main"` fast-forwards the main branch, for development; `"release"` checks out the newest `vX.Y.Z` tag, only when a newer one is out, and never goes backwards. The desktop app's own copy uses `release` ([1_setup.md](1_setup.md#desktop-app)); the app's History is in [0_00_design.md 4.5](0_00_design.md#45-history).

The service token only signs a client in: the app, or each CLI command, gets its own token with it, which expires ([0_06_security.md 1](0_06_security.md#1-rules)). Rotating the service token leaves signed-in clients alone; add `--revoke-clients` to sign them out too. `service clients` works on `~/.agentop/state/clients.json` directly, so it works while the service is stopped, and a running service notices at once. Running it as a system service or behind a proxy is in [1_setup.md](1_setup.md).
