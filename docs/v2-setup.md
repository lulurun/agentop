# Running v2

v2 is a service plus an app. Each machine that runs agents runs the service, and
the app connects to any service it can reach. The app is served by the service
at `/app/`.

## On a machine of your own

Needs Python 3.11+, tmux, and Node 20.19+ or 22.12+ to build the app.

```bash
git clone <repo> agentop && cd agentop
pip install -e .
(cd ui && npm ci && npm run build)   # the build output is not committed
agentop serve                        # http://127.0.0.1:9775
agentop open                         # opens the app, signed in
```

As it starts, `agentop serve` checks the host:

- It looks for each agent tool's program (`claude`, `codex`, `agy`) on the PATH of the user's login shell, where sessions run, and on its own. It refuses to start when it finds none. The New session dialog offers only the tools it found; restart the service after installing another.
- It installs or updates agentop's skills ([src/agentop/skills/](../src/agentop/skills/README.md)) for each tool found that takes them: for now Claude Code, in `~/.claude/skills/`.

## The devhost, behind pisces-01

The service binds `127.0.0.1:9775`. `eiger-tunnel` forwards it to `pisces-01:7775`,
and nginx there serves it at `http://157.120.33.185:7700/agentop/`.

The proxy has no authentication, and plain HTTP carries the service token where a
network observer could read it. This is accepted for now: see plan section 9.1.

Eiger owns this setup: the `agentop-api` systemd unit that runs `agentop serve`
(`Eiger/deploy/agentop-api.service`, linked into `~/.config/systemd/user/`), the
tunnel, and the nginx config. agentop itself only needs `agentop serve`.

**nginx must forward WebSockets.** The session list and the terminal both use them.
The config is generated by `potential-panda/Eiger/tunnel/setup.sh`, which sets
`Upgrade` and `Connection` for grafana and agentop. Without them the app connects
and then says the service can't open a live connection.

To deploy, use Update in the app's service status, or from the main checkout:

```bash
(cd ui && npm ci && npm run build)
systemctl --user restart agentop-api
```

Restarting leaves tmux sessions running. The old dashboard then stops working
through the proxy, and `/agentop/` leads to the app. On the devhost itself it still
works at `http://127.0.0.1:9775/`.

Print the address to paste into Connect to a service:

```bash
agentop service connect-info --url https://agentop.wolfdrawer.net
```

### HTTPS

The devhost is also at `https://agentop.wolfdrawer.net`, which is the address to
use. `Eiger/tunnel/wolfdrawer/setup-wolfdrawer.sh` installs it as its own nginx site with a
Let's Encrypt certificate, and `certbot.timer` renews it. To remove the site, delete
`/etc/nginx/sites-enabled/wolfdrawer` on pisces-01 and reload nginx.

It uses port 443, not 7700: nginx can't mix TLS and plain HTTP on one port, and the
other apps on 7700 are plain HTTP.

## Connecting from the app

Load the app from your own machine's service, `http://127.0.0.1:9775/app/`, then use
Connect to a service in the service menu. A browser allows a loopback page to reach other
addresses. A page loaded from the proxy can use only the proxy: it can't reach your
machine's loopback.

## Controlling a service

```bash
agentop service status
agentop service stop       # or restart. Sessions keep running
agentop service update     # pull, install, build, restart; goes back if that fails
```

The same actions are in the app, in each service's Status. The CLI and the app both
ask the running service, which knows whether systemd runs it or it was started with
`agentop serve`, and acts on itself. Started by hand, restart runs it again in the same
terminal.

Nothing starts a stopped service, since it isn't there to answer. Start it on its
machine with `agentop serve`, or with the system service that runs it. Until then the
app shows a red dot and says so.

`update` needs a clean checkout on `main` that can reach its git remote, not
systemd. It writes
progress to `~/.agentop/state/update-status.json` and detail to `~/.agentop/logs/update.log`.
If the new version fails to install or start, it resets to the previous commit and
says so, and the failed commit stays on the remote until it is fixed. If a service
started by hand died starting the new version, the update starts it again in the
background, logging to `serve.log`.

## Desktop app

Needs everything above, plus Rust and the WebKitGTK 4.1 development files. On Arch
those are `webkit2gtk-4.1`, `gtk3`, `libsoup3`, and `librsvg`.

```bash
(cd desktop && npm ci && npm run build)     # binary in src-tauri/target/release/
(cd desktop && npm run package)             # a .deb in src-tauri/target/release/bundle/
```

The app connects to this computer's service by itself, reading `service.json`, and
keeps other services' tokens in the OS keychain, which needs a running secret service
such as GNOME Keyring or KeePassXC. Unlike a browser, it has no rule against reaching
either loopback or plain HTTP addresses, so HTTPS-Only Mode and similar limits don't
apply.

If this computer's service is stopped, the app says so and how to start it, as the web
app does. It can't start it either.

## Old routes and proxies

The old routes have no token, so requests with forwarding headers
(`X-Forwarded-For`, `X-Real-IP`, `Forwarded`) are refused on them, whatever their
Host. Adding a name to `AGENTOP_ALLOWED_ORIGINS` lifts that for the name, which
makes the old terminal public on an open proxy, so don't list pisces. `/api/v2` and
`/app/` are unaffected, because `/api/v2` requires the token.
