# Review, November 2026

Suggestions from an outside review of agentop, kept so none is lost. Nothing here is a plan or a commitment: each item is a suggestion for the owner to take, change or drop.

- **Date:** 2026-11-17. **Reviewed at:** commit `ad9a89a` on `main`. Every file:line below was checked again at that commit.
- **How:** a read-only review. The code and docs were read; the test suite was not run (pytest is not installed in the local environment, and nothing was installed). The UI and the desktop app were not run either.
- **Two rounds.** The first round read the code and listed findings. The second round came after the owner explained what the project is for, and re-ranked them around that.
- **Who it is for.** agentop answers four needs: (1) several isolated tasks, each with its own agent CLI, on your own subscriptions; (2) carrying on from your phone, away from the office, and coming back to the same session; (3) one window for all of it, across hosts; (4) passing work between sessions, so each keeps its own context. tmux is the mechanism agentop chose for them, hidden from the user; it is not a habit the user needs.
- **Status of each item:**
  - **PROVEN LIVE**: shown by running code. Only one item is, the dialogue PID signal (1.4), by a one-off script run before the review became read-only.
  - **READ IN CODE**: the mechanism is in the code; the effect at runtime was inferred, not seen.
  - **IDEA**: a design suggestion, not a defect.
  - **DELIBERATE**: a choice the owner made on purpose; the residual risk is noted.

## 1 Ranked priorities

These six follow the second round's ranking, with one change from the owner: handoff (1.2) serves a core need, keeping each session's context clean and focused, so its suggestions (an idle check before pasting, delivery confirmation, a visible record of handoffs) move up from sixth to second. CI stays first, because it guards everything else, handoff's paste included. The second round's order was CI, token renewal, PID check, remote control, dialogue turns, handoff.

### 1.1 Run the tests in CI on every push

- **What:** nothing runs the tests. `.github/workflows/release.yml` and `desktop.yml` only build and release on tags; pytest is only in the `dev` extra (`pyproject.toml:18`).
- **Why it matters here:** the agent CLIs update often (the second round said weekly), and the parts that depend on them break silently: `send_text` paste then Enter (`src/agentop/agentclis/base.py:49`), the trust-prompt handling (`src/agentop/agentclis/claude.py:228`), idle detection (`src/agentop/actor.py:44`), and the screen parsers. Tests that exist but don't run catch nothing.
- **Status:** READ IN CODE.
- **Suggested fix:** a workflow on every push that runs pytest, vitest, `tsc` and `cargo test`; Playwright nightly. IDEA, not from either round: a small scheduled job that starts each installed CLI in tmux and checks the ready marker and a paste, to catch CLI updates.

### 1.2 Handoff: check the target is idle, confirm delivery, and record each handoff

- **What:** `agentop send` pastes and presses Enter whatever the target's screen shows: mid-turn, a permission dialog, a menu (`src/agentop/ops.py:214`, `src/agentop/agentclis/base.py:49`). Claude Code queues typed input while it works (per design 12.10.3, not checked here), but a menu or dialog could take the keys; what Codex and Antigravity do was not checked. `ok` means the keys were typed, not that the target took the task. There is no record of handoffs the app shows.
- **Why it matters here:** handoff answers need (4). Long-lived sessions come to hold a role and its context (dev on a feature, deployment, prod support mid-investigation), and work that belongs to another role is handed to the session that already holds that context, so neither has to be polluted or rebuilt. That only works if the task arrives: a prompt lost in a menu fails silently while the sender carries on, and with no record the owner can't see what was handed where.
- **Context:** [design 12.10.3](design.md#12103-dropped-the-handoff-plugin-2026-11-13) dropped idle-only delivery, an audit log and a Handoffs view on purpose, because the owner watches the target. These suggestions are a lighter version of that, not a reversal.
- **What Memory already holds:** the messages table keeps the sender's `/handoff ...` prompt (`tests/test_memory_messages.py:37`, `:211`), and the target's transcript has the prompt starting `[agentop send from <sender>]` (`src/agentop/cli.py:256`). So both ends are searchable in Memory today, but nothing links them or lists handoffs as such.
- **Status:** READ IN CODE (the gaps); IDEA (the fixes).
- **Suggested fix:** idle check: before pasting, check the target's screen for its ready marker (as `post_start_hook` does) and refuse or wait when it is not ready. Delivery confirmation: after pasting, check the prompt appeared in the target, and report that, not just that keys were typed. Visible record: list handoffs from the `[agentop send from …]` prompts Memory already indexes, rather than adding a store.

### 1.3 Token renewal rebuilds the client, so terminals reattach

- **What:** `useMemo(() => activeClient(...), [connections, activeId])` builds a new `ServiceClient` whenever `connections` changes (`ui/src/components/MainArea.tsx:273`; `activeClient` is `ui/src/store.ts:319`). `updateConnection` replaces that array on every renewal, including another saved service's (`ui/src/store.ts:643`). `TerminalView`'s effect depends on `client` (`ui/src/terminal/TerminalView.tsx:246`), so the terminal is disposed and reattached. The same pattern is in `ui/src/plugins/dialogue/index.tsx:170`, `ui/src/components/FilesSection.tsx:22` and `ui/src/plugins/Slot.tsx:29`, and the dialogue and Memory state reset when their client changes (`ui/src/plugins/dialogue/state.ts:117`, `ui/src/plugins/memory/state.ts:121`).
- **Why it matters here:** this hits the flow the owner built the UI for ("99% of my work in one window", in the owner's words), with several services saved: about once an hour per service, the open terminal could reattach and the dialogue or Memory view could reset.
- **Status:** READ IN CODE. The mechanism is in the code; the reattach was not seen running.
- **Suggested fix:** one stable `ServiceClient` per connection, which reads the current token when it sends; memoize on the connection's id and URL, not on the array.

### 1.4 Check a saved PID before signalling it

- **What:** two places send a signal to a PID read from a file, with no check that it is still the process that was started:
  - **Dialogue.** The runner's PID is saved in `meta.json` (`src/agentop/plugins/dialogue/ops.py:115`, `:121`) and later gets SIGTERM on Stop (`ops.py:522`) and, through `_close_open_sessions` (`ops.py:290`), on Remove and when the plugin is turned off.
  - **Desktop app.** It adopts the PID in `desktop-serve.pid` if `kill(pid, 0)` succeeds (`desktop/src-tauri/src/service.rs:115`), and on exit sends it SIGTERM, then SIGKILL (`service.rs:177`, `:316`). Adoption is tested only by an `#[ignore]` integration test (`service.rs:411`).
- **Why it matters here:** after a crash or a reboot the PID can be reused, and Stop, Remove or quitting the app would then kill an unrelated process of the owner's.
- **Status:** dialogue PROVEN LIVE: a one-off script (not part of the repo's tests), with a private home and a stubbed dependency, saved the PID of a `sleep` it had started itself as a dialogue's PID; `stop_dialogue` sent the `sleep` SIGTERM (exit -15). Desktop READ IN CODE.
- **Suggested fix:** save the process start time and command line beside the PID, and compare them before signalling; skip the signal on a mismatch.

### 1.5 Make remote control plus skip-permissions an explicit, documented choice

- **What:** every Claude session starts with `claude --dangerously-skip-permissions --remote-control`, and resumes the same way (`src/agentop/agentclis/claude.py:84`, `:132`). The bridge URL is read from the session (`claude.py:300`) and shown in the details panel (`ui/src/components/DetailsPanel.tsx:196`). Codex and Antigravity sessions start without a remote-control flag (`src/agentop/agentclis/codex.py:131`, `src/agentop/agentclis/antigravity.py:83`).
- **DELIBERATE:** remote control is on so the session shows up in the Claude mobile app (the owner's choice; design.md does not record it). Skip-permissions is a documented choice ([design section 7](design.md#7-security)).
- **Why it matters here / residual risk:** remote control is an access path outside agentop's tokens: anyone who reaches the owner's claude.ai account can drive the session. Skip-permissions removes even the approval step on that path. Design section 7 does not mention it.
- **Status:** READ IN CODE.
- **Suggested fix:** keep it on by default, but make it a visible per-session option at start, and add it to design section 7 as an access path.

### 1.6 Dialogue: write each turn to a file

- **What:** a dialogue turn pastes a prompt, waits until the screen has been still for 5 s (`idle_seconds`, `src/agentop/agentclis/base.py:45`; 15 s for Antigravity, `antigravity.py:67`; the loop is `src/agentop/actor.py:44`), then scans the scrollback for a `--- BEGIN <name> turn:N nonce:X` ... `--- END` block (`src/agentop/plugins/dialogue/parser.py:22`).
- **Why it matters here:** dialogue is the most original part, and this is its most fragile mechanism. A still screen does not mean the turn is done; the text is read back from what the TUI draws (wrapping, restyling, long replies scrolling out); and it depends on each tool's rendering, which changes with CLI updates. One such workaround is already there: matching with `in` so Claude Code's `●` prefix doesn't break detection ([dialogue.md](dialogue.md)). The concrete failure: when the screen is still but no END block is there, the orchestrator pastes a recovery prompt into an agent that may still be working, and after its retries fails the turn (`src/agentop/plugins/dialogue/orchestrator.py:137`). The parser has no direct test.
- **Status:** IDEA, untested.
- **Suggested fix:** have each agent write its turn to a file in the dialogue folder and signal that it is done, and read the file rather than the screen. Check the tools' turn-end hooks (Claude Code has a Stop hook) as the done signal. Design 12.11 already prefers transcripts to the screen for the same reasons.

## 2 Other findings, by area

Each item: what, why it matters for the owner, status, and a suggested fix.

### Core and service

- **`clients.json` has no cross-process lock.** The CLI writes it too (`src/agentop/cli.py:286`, `:314`), unlike the registry. *Why:* running `agentop service clients --revoke` while the app renews could drop one of the two writes; the window is small. READ IN CODE. *Fix:* take the same `flock` as `registry.py`.
- **`authenticate` changes `_clients` on threadpool threads without a lock.** `require_client` is a sync dependency (`src/agentop/service/routes.py:154`), so it runs on worker threads (`src/agentop/service/auth.py:166`). *Why:* the phone signing in while the desktop app makes requests could raise "dictionary changed size" for one request. Rare. READ IN CODE. *Fix:* a lock around `_clients`.
- **The service-token lockout is global** (10 wrong tries a minute, `auth.py:37`). *Why:* the window slides (`auth.py:136`), so someone who keeps guessing keeps the owner from adding a client, such as a new phone browser, for as long as they go on. DELIBERATE (behind a proxy, all callers look alike). *Fix:* none suggested.
- **Open CORS, and no `Origin` or `Host` allowlist** (`src/agentop/service/routes.py:143`; [design 7.1](design.md#71-rules)). *Why:* it is what lets the app connect to any reachable service. DELIBERATE. *Residual risk:* any web page can learn that a service is up (`/health`) and read `/auth/methods`; the token is the only barrier; and a page the owner visits could post wrong service tokens to trip the global lockout above (browsers may block this for loopback, not for a service behind a proxy). *Fix:* none suggested.
- **Skip-permissions on Claude and Antigravity sessions** (`claude.py:84`, `:132`, `antigravity.py:83`, `:137`; Codex starts with `--dangerously-bypass-hook-trust` only, `codex.py:131`; [design section 7](design.md#7-security)). DELIBERATE. *Residual risk:* a token already gives a shell, so the added risk is no human approval step when an agent follows injected instructions, from a file, web content, or a prompt another agent sent with `agentop send` (accepted for now in design 12.10.3).
- **`GET /history` writes to the registry** (`routes.py:405`), a side effect in a GET. *Why:* opening History changes stored state, which makes history bugs harder to reason about. READ IN CODE. *Fix:* move the write to the history scan.
- **`/fs/dirs` browses the whole filesystem** (`routes.py:326`). *Why:* it lets the owner pick any folder for a new session. DELIBERATE; behind the token. *Fix:* none suggested.
- **`at_limit()` runs outside the lock** (`src/agentop/service/store.py:366`). *Why:* starting sessions from two places at once (phone and PC) can go over `max_active`. READ IN CODE. *Fix:* check and record under one lock.
- **`--model` is added to a shell command line unquoted** (`src/agentop/agentclis/base.py:165`). Today the value only comes from code, and the one caller passes none (`src/agentop/plugins/dialogue/ops.py:86`). *Why:* harmless now; a value with spaces or shell characters would break the launch command, and it would be injection if the value ever came from a file such as a scenario or brief. READ IN CODE. *Fix:* `shlex.quote` it.

### Plugins

- **Isolation is fault isolation, not a sandbox.** `register` and event handlers run under `wait_for(to_thread(...))` (`src/agentop/service/plugins.py:314`, `:450`); a timeout leaves the thread running and holding an executor worker. `api.task` coroutines and async plugin routes run on the event loop (`plugins.py:377`), so a blocking call there stalls the whole service, though the module docstring says nothing a plugin does can block the loop for long (`plugins.py:8`). *Why:* one slow plugin would freeze every terminal and session the owner has open. READ IN CODE. *Fix:* say "fault isolation" in the docstring and design 12, or run plugin tasks off the loop.
- **Re-import clears `sys.modules`** for the plugin (`plugins.py:345`). *Why:* a `register` thread that timed out (`plugins.py:314`) keeps running against the old module after the plugin is turned off and on again. READ IN CODE. *Fix:* none suggested beyond the item above.
- **Memory summaries run an agent CLI headless** (`src/agentop/plugins/memory/__init__.py:49`, on by default; the first installed of `claude --print`, `src/agentop/agentclis/claude.py:99`, or `codex exec`, `src/agentop/agentclis/codex.py:101`). Design 12.11 documents this, but [design 12.10.2](design.md#12102-transport-tmux-only) says agentop does not run agents headless. *Why:* "no LLM API" holds, but 12.10.2 itself says headless `claude -p` usage is billed apart from interactive use. READ IN CODE. *Fix:* correct 12.10.2, and note the billing point in 12.11's summaries phase. (Found while checking the README for this review.)

### Dialogue

- The PID signal (1.4) and file-based turns (1.6).
- **`meta.json` is written non-atomically** with `write_text` (`src/agentop/plugins/dialogue/model.py:82`) by both the runner and the service. *Why:* the Dialogues workspace can read a half-written file and show a dialogue as missing or broken. READ IN CODE. *Fix:* write a temp file and rename it.
- **`DialogueMeta.load` falls back to a glob** `*{id}` (`model.py:144`). *Why:* with many dialogues, a short id could match another folder and Stop or Remove the wrong one. READ IN CODE. *Fix:* require exactly one match.

### Handoff

- See 1.2, ranked second because handoff serves a core need. The skill's prompt template (Task, Change, Code, Done when, Ask the user before, optional Reply) is well designed (`src/agentop/skills/handoff/SKILL.md`), and handoff as a skill plus `agentop send`, not a plugin, is the right weight. No change suggested.

### UI

- Token renewal (1.3).
- **Late replies can land on the wrong service.** `act`, `loadHistory` and `resumeHistory` are not tied to a connect attempt (`ui/src/store.ts:676`, `:682`, `:736`). *Why:* switching between devhosts mid-request could show one service's history on another. READ IN CODE. *Fix:* capture the connection id before the await and drop the result if it changed.
- **Keychain writes are not awaited.** `token_set` is fire-and-forget (`ui/src/platform/tauri.ts:89`), so `syncCredentials` (`ui/src/store.ts:487`) could pair a new `issuedAt` with an old token. *Why:* the desktop app could sign the owner out after a renewal. READ IN CODE. *Fix:* await the write.
- **There is no app-level error boundary** (`ui/src/main.tsx:13`). A plugin's `tabLabel` and `action.run` run outside any boundary (`ui/src/components/Workbench.tsx:29`, `ui/src/components/WorkspaceNav.tsx:89`). `PluginBoundary` renders nothing and never resets (`ui/src/plugins/Slot.tsx:9`). *Why:* one render error blanks the one window everything runs in. READ IN CODE. *Fix:* a top-level boundary with a reload button; a reset key on `PluginBoundary`; wrap plugin calls.
- **A 401 on a terminal ticket leaves the terminal on "connecting"** (`ui/src/terminal/TerminalView.tsx:176`). *Why:* other requests and the events socket do bring up "Signed out of …" on a 401, but when only the ticket request fails the terminal tab gives no reason. READ IN CODE. *Fix:* show "signed out" in the tab.
- **External Markdown images may be blocked in the desktop app.** The viewer renders them (`ui/src/plugins/viewer/Markdown.tsx:76`), but the desktop CSP has `img-src 'self' data:` (`desktop/src-tauri/tauri.conf.json:21`). *Why:* READMEs with badges or remote images would show broken. READ IN CODE; whether that CSP applies to the service's page was not checked. *Fix:* check, then allow `https:` images or proxy them.
- **The UI itself is justified**: one window for the work, the fold phone, other hosts; narrow-screen layouts are in `ui/src/styles.css:847` and `:981`. No change suggested.

### Desktop

- PID adoption (1.4).
- **It trusts whatever answers `/health` on the port.** If something answers on the configured port (9775 by default), the app treats it as its own service (`desktop/src-tauri/src/service.rs:113`, `:254`) and grants that origin the commands that return the service token and use the keychain (`desktop/src-tauri/src/main.rs:47`, `:133`, `:170`). *Why:* on a shared host another user's process on that port would get the token; on the owner's single-user hosts this matters much less. READ IN CODE. *Fix:* check the instance id in `/service` against `service.json` before trusting it.

### Tests and CI

- No CI (1.1).
- **Gaps:** no direct tests for `scanner.py`, `actor.py`, the session-meta parsing in `claude.py` and `antigravity.py`, the dialogue `parser.py`, or `ClientStore` concurrency. vitest covers pure modules only (`src/**/*.test.ts`), with `store` only partly covered. The Rust start, stop and adoption test is `#[ignore]` (`desktop/src-tauri/src/service.rs:411`). The `tmux_server` fixture that isolates tmux is opt-in, not autouse; other files set `AGENTOP_HOME` themselves. *Why:* the untested parts are the ones CLI updates break. READ IN CODE. *Fix:* with CI in place, add parser and idle-detection tests first, from screens captured from each CLI.

### Docs

- **`docs/design.md` is long** (about 1170 lines) and reads partly as a dated journal. *Why:* finding the current design takes reading its history. IDEA. *Fix:* move the history into a changelog and keep the design current.
- **Remote control is not in design section 7** (1.5).
- **Under systemd, sessions survive a service restart only if the unit uses `KillMode=process`** (`docs/design.md:50`); agentop ships no unit, and neither the README nor setup.md says so. *Why:* a user-written unit left at the default kill mode could take the tmux server down with the service, against "sessions outlive everything else". READ IN CODE (docs only; not run). *Fix:* add a `KillMode=process` note to setup.md and the README's system-service sentence. (Found in review round 3.)

## 3 What the review found strongest

- **tmux as the base is the project's best decision.** The subscription CLIs stay as they are: no LLM API, no chat view in their place. Sessions survive the app closing, service restarts and leaving the office, which is what makes PC to phone and back work. Every tool is driven the same way (paste or send-keys, then read the screen), so handoff and dialogue work across Claude Code, Codex and Antigravity with very little per-tool code: `ops.send` is about 20 lines (`src/agentop/ops.py:214`). tmux is the means, not the audience: agentop turns it into a task-named list of sessions plus a control panel, and the user needs no tmux knowledge.
- **The terminal bridge** has real backpressure (the reader is removed while a send is in flight) and clean teardown: terminate, then kill, then wait, in its own process group (`src/agentop/service/terminal.py:48`, `:104`, `:136`).
- **Tokens:** only hashes are stored, compared with `hmac.compare_digest`; WebSocket tickets are single-use, 30 s and scoped; renewal has a grace period; revoking a client closes its sockets; the service refuses a non-loopback bind without TLS (`src/agentop/service/app.py:94`).
- **Plugins fail on their own:** time limits, error budgets, and public routes only for plugins in the `login` slot (`src/agentop/service/plugins.py:314`).
- **The registry** is locked across threads and processes (`src/agentop/registry.py:36`).
- **Tool differences stay in `src/agentop/agentclis/`.**
- **Markdown is sanitized** with GitHub's schema, and highlighting runs after sanitizing (`ui/src/plugins/viewer/Markdown.tsx:94`).
- **In the UI:** connect attempts are numbered so stale replies are dropped (`ui/src/store.ts:329`); the service token is never saved (`ui/src/store.ts:235`); tabs renew under a Web Lock (`ui/src/store.ts:517`); each plugin's API client is scoped to its own routes (`ui/src/plugins/Slot.tsx:30`); the desktop capabilities are narrow (`desktop/src-tauri/src/main.rs:133`).
- **The Memory sweeper** releases its waiting threads when it is cancelled, so a restart does not hang (`src/agentop/plugins/memory/__init__.py:123`).
- **Tests exist:** 24 pytest files (about 370 cases by the first round's count, not collected here), vitest for the pure UI modules, and 6 Playwright specs that run against a real service and a private tmux server.

## 4 Scope

The first round named Memory, dialogue and email code as each product-sized; the second round named attention, email code and Memory. The backlog adds Windows, macOS signing and host support, service and UI updates, and pairing ([plan section 9](plan.md#9-backlog)). With one maintainer and no CI, the suggestion is to hold off on new plugins until CI (1.1) exists.
