# Input bar plugin

Type prompts in a box below the terminal: plugin `input` (`src/agentop/plugins/input/`, UI in `ui/src/plugins/input/`). On by default, on every device. How plugins work in general is in [0_12_00_plugins.md](0_12_00_plugins.md).

agentop leaves the agent's interface to the agent tool in tmux, and stays out of being a chat app. Two things made a box worth adding anyway:

- **Phones.** Typing into a terminal on a phone is poor: the keyboard covers it, autocorrect and Japanese input fight xterm, and there is no Esc.
- **Drafts.** In a project the owner mostly talks to the Coordinator, which hands tasks to other sessions, and their replies come back with `agentop send` while the owner is typing. Typed in the terminal, the draft sits in the tool's own prompt box, so the reply's paste joins it and its Enter submits both. Typed in the bar, the draft stays in the browser, the tool's box is empty, and the reply arrives as its own prompt (queued by the tool while it works).

The bar adds a text box below the terminal instead of replacing anything: the terminal still shows everything, and only where the typing goes changes.

## 1 How it works

- The `terminal-input` UI slot draws a plugin's piece below a session's terminal (`TerminalInputs` in `ui/src/plugins/Slot.tsx`). The piece calls `terminal.takeInput(true)` while it takes the input. While any piece does, the terminal is only watched (`TerminalView`'s `typing={false}`): keys are dropped, and a tap doesn't raise the phone's keyboard (its textarea is read-only with `inputmode="none"`). Mouse reports still go through (`terminal/mouse.ts`), so wheel and finger scrolling reach tmux as before, and a click on the terminal moves the keyboard to the box.
- It is not the read-only attach dialogues use (`-f read-only,ignore-size`): that keeps the window's size and shrinks the font to fit, unreadable on a phone looking at a window sized by a desktop. Here the terminal still sizes the window to the tab.
- A piece that unmounts, or crashes (its error boundary's `onFail`), gives the input back, so a broken plugin leaves an ordinary terminal.
- A prompt goes to `POST /api/v2/plugins/input/sessions/{id}/prompt {text}`, which types it with the tool's own `AgentCli.deliver`, as `agentop send` does: a bracketed paste, so lines stay one prompt, then Enter. An empty prompt presses Enter alone.
- A key button goes to `…/keys {keys}`, one of a fixed set (Esc, arrows, Enter, Tab, Shift-Tab, digits) sent with `tmux send-keys`, for what a paste can't do: choosing in a menu, interrupting with Esc. Both routes first take the pane out of copy mode, where scrolling back leaves it.
- **^B, tmux's prefix.** Pressing it arms the prefix; the next text or key button is typed as Ctrl-B and then that text, with no Enter: ^B then `c` makes a window, ^B then `2` goes to window 2. It can't go through `send-keys`, which hands keys to the program in the pane and skips tmux's bindings, so it goes through the terminal's own tmux client, as if typed on its keyboard (`TerminalInputControl.type`). That works while the terminal ignores typing. It assumes the default prefix, Ctrl-B.
- Only a running session agentop started, and not a `readonly` one, takes prompts, as with `agentop send`. On any other the bar doesn't show and the terminal is typed into as before.

**One queue.** `agentop send` goes through the service (`POST /api/v2/send`), so it and the bar type in one process. There `AgentCli.deliver` holds a lock for each tmux session (`agentclis.base.typing`), as do the bar's Enter and key buttons: a prompt waits for the one before it, and never lands between its paste and its Enter. Typing straight into the terminal still works, and is outside the queue.

**Per device, not per service.** A plugin's switch belongs to the service, so it can't choose for each client. The plugin being on makes the bar available; each device then chooses, in localStorage (`agentop.input.mode`), and a device that hasn't chosen shows the bar. The ⌨ button in the bar switches to typing in the terminal and back, and the choice holds for every session on that device. It is also the way out when an agent shows a menu that the key buttons don't cover.

## 2 In the box

- On a touch screen Enter is a new line, as on a phone; with a keyboard Enter sends and Shift+Enter is a new line (not while an IME is composing, so Japanese input confirms its word first). The send button, or Ctrl or Cmd with Enter, always sends.
- Each session's unsent text is kept in localStorage until it is sent.
- Buttons don't take the focus, so the phone's keyboard stays up between a key and the next line.

## 3 How it looks

A composer card: the text box on top, a toolbar inside the card below it, and the card's outline lights up while it has the focus. The placeholder names the session (`Message Coordinator`). The toolbar has the keys in groups (^B and Esc, the arrows and Enter, Tab, the digits), a hint for a new line on a wide screen, ⌨, and the send button at the right. That button is grey with an Enter mark while the box is empty, since sending nothing presses Enter, and filled with the action colour once there is text. ^B armed turns the card's outline and the send button amber. On a touch screen the keys are 36px high and the row fades at its right edge, where the keys that don't fit scroll.

## 4 Reception

A session's context only grows, and a Coordinator can't judge "this request is unrelated, clear first" without the request already sitting on top of its long history. Reception makes that call before the prompt goes in, and only ever suggests: the owner decides.

- **The switch** is per session and kept on the service (the plugin's `store.json`, keyed `<project>/<name>`, so it survives a resume), not per device: phone and desktop behave alike. It is on by default for a Projects project's Coordinator and off for every other session. The toolbar's reception button turns it on and off; a dot shows it is on.
- **Sending** with it on: the bar holds the prompt and asks `POST …/sessions/{id}/check {text}`. Without asking a model, a prompt passes when it is short and one line (40 characters: "please continue"), a slash command, or the session has had fewer than 3 prompts. Otherwise a cheap model (the first tool with a one-shot command, as Memory's summaries use: Claude's Haiku) reads the session's first prompt, its latest messages back to 12,000 characters, the new prompt, and for a Projects Coordinator the Objective and Next of `STATE.md`, and answers `keep` or `clear` with one sentence why. It first names the current work, the thread of the latest messages rather than the project, and what the prompt asks for: `keep` when the prompt needs that thread, `clear` when it starts other work, even in the same project. A Coordinator rereads its state from files, so for it the check leans to `clear`; otherwise, when unsure, `keep`. It takes about 3 seconds; a failure or a 20-second timeout passes the prompt.
- **Keep** sends the prompt as usual. **Clear** keeps it in the box and shows "This looks like new work" with the reason, and three choices: **Clear context & send**, **Send as is**, **Keep editing** (also Esc, or changing the text). While it checks, **Send now** skips the check.
- **Clear context & send** types `/clear` (Claude and Codex both start a new conversation on it), waits for the screen to settle, then types the prompt. A Coordinator's prompt starts with a line telling it to read AGENTS.md, COORDINATOR_SKILL.md and STATE.md (those present), and in a Projects project to run `agentop task list`, before answering.
- **The record**, `~/.agentop/plugins/input/reception.jsonl`: each model check (verdict, reason, the current work and the prompt as the model read them, model, time taken) and the owner's choice against it, so how often the check is right can be read before deciding whether it should ever clear on its own ([7_coordinator-dogfooding.md](7_coordinator-dogfooding.md)).
