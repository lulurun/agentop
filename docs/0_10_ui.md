# UI layout

The app's layout is fixed. This page names each part of it, says what goes where, and gives the keys that reach each part. Why the UI is shaped this way is in [0_00_design.md section 10](0_00_design.md#10-ui). Plugins fill this layout; they don't add parts to it (see [Rules for plugins](#rules-for-plugins)).

## The parts

```
┌──────────────────────────────────────────────────────────────────────────────┐
│ [A]  ● devhost ▾   Sessions  Dialogues  Memory        [⚙] [◧] [◫] [◫] [◨]  │  header
├──────────────┬───────────────────────────────────────────────┬───────────────┤
│ ▾ Section    │ [tab][tab][tab]       │ [tab][tab]            │ ▾ Section     │
│   …          │                       │                       │   …           │
│ ▾ Section    │   buffer              │   buffer              │ ▸ Section     │
│   …          │                       │                       │               │
│              │   left area           │   right area          │               │
│ left panel   │            middle panel                       │ right panel   │
└──────────────┴───────────────────────────────────────────────┴───────────────┘
                                   body
```

| Name | What it is | In the code |
|------|------------|-------------|
| **Header** | The bar across the top | `App.tsx`, `.header` |
| **Brand** | The agentop icon, `public/logo.svg`; not a control | `App.tsx`, `.brand` |
| **Connection manager** | Which service the app is connected to: switch, add, Status of each | `ServiceSwitcher.tsx` |
| **Feature nav** | One button per feature, the current one highlighted | `FeatureNav.tsx` |
| **Feature** | A top-level part of the app: Sessions (core, the `default` project), Projects, Dialogues and Memory (plugins), more from plugins. Each has its own left panel, right panel, background and tabs | `features.ts` |
| **Settings button** | Opens Settings, the app's own settings | `App.tsx` |
| **Layout toggles** | Four buttons after Settings: left panel, left area, right area, right panel. Each shows or hides its part ([Header](#header)) | `App.tsx`, `.header-tools` |
| **Body** | Everything below the header: left panel, middle panel, right panel | |
| **Left panel**, **right panel** | The feature's side panels. Their content is sections only | `.sidebar`, `.details` |
| **Section** | A titled part of a panel. Clicking the title folds it; a panel with one section still has its title | `Section.tsx` |
| **Middle panel** | Between the panels. Shows the background, or one or two areas | `MainArea.tsx`, `.main` |
| **Background** | What the middle panel shows with no areas: the feature's placard | a feature's `background` |
| **Left area**, **right area** | The middle panel split in two. Either can be there alone, and then fills the middle panel | `Workbench.tsx`, `Layout.left`, `Layout.right` |
| **Active area** | The area last used. Tab keys act on it, and the right panel follows its tab | `Layout.focused` |
| **Tab** | One entry in an area's tab bar; the area shows one tab's buffer at a time. A pinned tab can't be closed | `Tab` in `tabs.ts` |
| **Buffer** | What a tab shows: a session's terminal, a file, a past session, a service's Status, a plugin's view | `TabContent` in `tabs.ts` |
| **Dialogs, menus, toast** | Drawn over the layout by the core: Settings, the connection manager's menu, a tab's menu, an error | |

Tabs belong exclusively to the middle panel’s left and right areas. The left and right side panels contain sections and controls.

Both side panels are resizable and collapsible. Whether each is open is remembered per project in its layout ([Project layouts](#project-layouts)), and per client in a feature without a project. Below 900px they become overlays and start collapsed; below 600px the feature nav becomes a drop-down, so the header still fits on a phone.

### Panel widths

The boundaries between the parts of the body can be moved: left panel and middle panel, left area and right area, middle panel and right panel. Each boundary has a grip at its middle and lights up under the pointer.

- **Drag** a boundary, or focus it (Tab) and use **Left** and **Right** (16px; with Shift 64px), **Home** and **End**. **Double-click** puts it back to the default: left panel 256px, right panel 312px, the areas half and half.
- The middle panel takes what the side panels leave; the areas share it. A side panel is 180 to 800px wide, the middle panel keeps 320px beside them, and each area keeps 200px.
- A shut panel has no boundary, and its room goes to the middle panel; opened again, it has its width back. With one area there is no boundary between areas.
- In a narrower window the side panels are drawn narrower, each in proportion and not below 180px, so the middle panel keeps its 320px; what was set is kept, and they widen again with the window.
- Below 900px there are no boundaries: the side panels are overlays of their own width (300px at most), and one area shows.
- The widths and the split are kept with the rest of the layout: per project in its `layout.json` ([Project layouts](#project-layouts)); in a feature without a project, the side panels' widths per client (as whether they are open), and the split per connection and feature, in `localStorage`.

## The features

| Feature | Left panel | Middle panel | Right panel |
|---------|------------|--------------|-------------|
| Sessions (core) | New session; Active sessions; History | The start buffer in the left area; session tabs, past sessions, files, Status | The active tab's session: details, usage, files, actions |
| Projects (`projects`) | Projects (the Project button, which opens the New project buffer in the left area; the list); then the chosen project's Active sessions and History | As Sessions, plus the Coordinator’s Progress Viewer | As Sessions |
| Dialogues (`dialogue`) | Create new dialogue; In progress; Finished | Agent A in the left area, agent B in the right, view only; artifacts open in tabs | The dialogue: status, stats, artifacts, Stop and Remove |
| Memory (`memory`) | None | The Search tab, pinned first in the left area: recent sessions, or results under All, Sessions and Mentions. A conversation per tab in the right area, opened at the mention | The conversation's summary and session |

A plugin's feature shows only while the plugin is enabled on that service; switching to a service without the current feature falls back to Sessions. Each feature's own doc says more: [0_13_projects.md](0_13_projects.md#72-projects-plugin-projects), [0_12_02_dialogue.md](0_12_02_dialogue.md#8-in-the-app), [0_12_03_memory.md](0_12_03_memory.md#6-the-memory-feature).

### Sessions

- **The start buffer** opens from New session in the left area: a session starts from its first prompt. The prompt box, and below it the sessions started from it, newest first. Sending clears the box; the row shows the tool, model and folder agentop chose, and the first prompt when it differs from what was typed, for 3 seconds (Change, Launch now, Cancel), or asks for the folder, then the session opens in a tab beside the buffer. Its settings (the probe's tool and model, the tool order, idle hours) are behind the gear in the buffer. How the choice is made is in [0_04_start.md](0_04_start.md).
- **Active sessions** lists the `default` project's sessions agentop started, newest first, with a keyword filter (which also filters History) and the count against the limit (`3/20`): the project's own active sessions over the service's limit, which every project's sessions fill, so it shows full when the service is. Projects' Active sessions count the same way for their project. Agents started outside agentop aren't shown.
- **History** lists past sessions ([design 4.5](0_00_design.md#45-history)), with a keyword filter and a CLI filter, newest first by last use. A past session opens as a tab showing its conversation, with **Resume** and **Delete** (asks first; deletes the transcript from its tool, and agentop's records of it) in the buffer's bar; the right panel shows its details, what its transcript holds, and its files.
- Clicking a section's title folds it; which are folded is remembered in this browser.
- **Progress Viewer** appears in the chosen project's Coordinator details. It opens a closable buffer in the middle panel’s right area ([0_13_projects.md 7.2](0_13_projects.md#72-projects-plugin-projects)). Its Results by action lists each plan action's result files; a name opens the file in a tab in the other area.
- **Files**, in the right panel, has filter buttons for Changed, All and the tool's memory; Changed refreshes every 10s. The reload button at the right of its title fetches the list shown again, open folders included.
- **Actions**, the last section in the right panel for a running managed session, contains **Stop session**.

### The middle panel

What a session's buffer shows depends on its state:

| State | Shows |
|-------|-------|
| `starting` | Spinner, session name, and current step text |
| `running` | Terminal, focused |
| `exited` | Terminal with a banner: Resume, Close session |
| `failed` | The error, and the terminal if tmux exists |
| Reconnecting | Terminal dimmed, "Reconnecting…" |
| Service unreachable | The connection problem instead of tabs, with Retry, and in the desktop app for this computer's service, Start. Forget for a service other than this app's own |

The app asks its questions in the page (Stop session and Delete for good in a modal), never with `window.confirm`, `alert` or `prompt`: where a webview shows no such dialog, `confirm` answers no without a word.

The web app asks before the page is left while a terminal is open (`beforeunload`), since Ctrl+W closes a browser tab rather than deleting a word.

## Tabs

- Each connection keeps one tab layout per project, and one per feature that shows none, as Memory ([Project layouts](#project-layouts)). Switching projects or features and back keeps the tabs, the split, and what was selected; the right panel shows the session selected in that project.
- A feature that opens with no tabs shows its background, which offers its New action. A default tab is **pinned**: it can be moved but not closed. Memory's Search tab is pinned first in the left area (a plugin's feature names its pinned view as `home`).
- Sessions' tabs stay mounted, hidden, while another feature shows, so terminals keep their connection and scrollback.
- Each area also keeps the last 3 sessions it showed, hidden (`KEEP_SESSIONS` in `Workbench.tsx`), so going back to one shows the same terminal at once instead of attaching again. A kept session goes when the tab that showed it closes, or when the session does. Each kept terminal holds a WebGL context and a socket, and a browser allows about 16 contexts.
- The core owns the `session`, `status` and `past` kinds; `file` is drawn by the `file-viewer` plugin; a plugin adds views of its own through its feature. When a plugin is turned off, its tabs close with its feature.

## Where tabs open

- An action in the **left panel** opens its tab in the **left area**; an action in the **right panel** opens it in the **right area**.
- An action in the **header** (Status in the connection manager) opens in the left area.
- An action inside a **buffer** (a link in a Markdown file) opens in that buffer's area.
- If the target area isn't there, it is made, and the middle panel shows it beside the other area if there is one.
- A session's tab opens in Sessions when it is in the `default` project, and in the feature shown when it is in another project ([0_13_projects.md](0_13_projects.md)); each feature has its own selected session, which its right panel shows.
- A tab already open in either area is shown where it is instead of opening twice.
- By default a tab takes the place of the target area's tab of the same kind (a session replaces the session shown); Ctrl or Cmd-click or the middle button opens a new tab.
- When an area's last tab closes, the area goes; when both have gone, the background shows.
- A tab can be moved to the other area from its menu. The tab bar has no split button: a session or file is shown in both areas by opening it in the other one by name, such as Open in the right area in a session row's menu.

Two exceptions: picking a dialogue in Dialogues' left panel shows agent A in the left area and agent B in the right one; and a session or mention in Memory's Search tab opens in the right area, beside the search.

## Project layouts

Open sessions, files and tabs belong to a project. Sessions is the `default` project, Projects shows the project picked in its left panel, and Dialogues the dialogue picked (each dialogue is a project). Each of these projects has its own layout, so switching from project A to B and back shows A's buffers again, in the same areas, order and tabs, with A's panels, and B never shows one of A's. Memory, and Projects or Dialogues with nothing picked, belong to no project: their tabs are kept per client, as before.

**Where.** `~/.agentop/projects/<project>/.project/layout.json`, on the service, beside the project's `project.json` and `sessions.json`; Sessions' is `default`'s. It is in `.project/` rather than the folder's top level because the top level is the agents' working space: a dialogue's agents work in it, and a Coordinator's notes and plans go there. The app reads and writes it with `GET` and `PUT /api/v2/projects/{name}/layout`, which take a client token like every other route, accept only the name of a project that exists (or `default`, made on the first save), and resolve the path on the service. `PUT` checks the whole file (below) and refuses anything else with 422.

**The format**, version 1, in the layout's own terms (the left panel, the middle panel's left and right areas, the right panel):

```json
{
  "version": 1,
  "left-panel": { "open": true, "width": 300 },
  "mid-panel": {
    "split": 0.4,
    "left": {
      "open": true,
      "tabs": [
        { "id": "start", "content": { "kind": "start" } },
        { "id": "t1", "content": { "kind": "session", "sessionId": "dev-a1b2c3" } }
      ],
      "active": "t1"
    },
    "right": {
      "open": true,
      "tabs": [{ "id": "t2", "content": { "kind": "file", "file": { "sessionId": "dev-a1b2c3", "source": "workdir", "path": "src/app.py" } } }],
      "active": "t2"
    }
  },
  "right-panel": { "open": false },
  "focused": "left"
}
```

- `open` is whether that part shows. An area with `open: false` shows nothing, whatever tabs it lists: one hidden with its header toggle keeps its tabs there, to show again; one that isn't there is written `{"open": false, "tabs": [], "active": null}`. When no area would show, the app shows the active one (or the one with tabs), and the active area is always one shown.
- `tabs` is the area's tabs in order, at most 64, each an `id` unique in the file and a `content`: `start`, `status`, `session` (`sessionId`), `file` (`file`: `sessionId`, `source` `workdir`, `memory` or `transcript`, `path`, optional `view: "diff"`), `past` (`historyId`), or `plugin` (`plugin`, `view`, optional `key`). `active` is the id of the tab the area shows.
- `focused` is the active area, `left` or `right`, which the tab keys act on.
- `width`, on `left-panel` and `right-panel`, is the panel's width in pixels, a whole number from 120 to 2000 (the app sets 180 to 800 and clamps a hand edit to that); `split`, on `mid-panel`, is the left area's share of the middle panel, 0.05 to 0.95 (the app sets 0.1 to 0.9). Each is optional: with none the default shows, and the app writes one only once it is set ([Panel widths](#panel-widths)). A value outside its bounds is refused with 422; one that isn't a number, in a hand edit, is ignored. A service older than these fields refuses them too, and the app then saves that file without them, so its tabs are still kept there.
- Pinned tabs are the app's: Sessions' start buffer is added first in the left area when the file doesn't list it, and isn't written as pinned.
- Below 900px the side panels are overlays that start shut, so there a project's `left-panel` and `right-panel` don't open them, and toggling them isn't saved.

**Defaults.** With no file, a project shows both side panels open and no tabs (its background; Sessions its start buffer), the left area active.

**Saving and loading.**
- The app saves a project's layout a moment after each change, and at once when another project, feature or service is shown and when the page is hidden or closed.
- It reads the file again each time a project is shown, after any save of it still on its way, so an edit by hand shows the next time the project is opened. Until a project's file has first been read, its middle panel shows nothing and changes to it wait; nothing is saved over a file the page hasn't read.
- Each project's loads and saves are queued on their own, per service and project, so a late reply lands only on the project it was for, and saves arrive in order. A reply that comes after the project was changed here is dropped: the change is newer, and is saved over the file.
- Saves go to the service they were made on, even after switching to another.
- An action still waiting when the owner moves to another feature, project or service (picking a dialogue, opening a project's Coordinator, a file, a resumed or new session) finishes in the view it began in, and leaves what is shown alone.
- Two clients showing the same project share its file: the last save wins, and the other client sees it the next time it opens the project.

**When the file is wrong.** One that isn't JSON or a JSON object, or is over 256 KB, is moved aside to `layout.json.corrupt-<time>` and the defaults show. One with another `version` shows the defaults; one from a newer app (a higher version) is never written over. Inside a version 1 file, the app keeps what it can: a tab it can't read, or with an id used twice, is left out or given a new id; a missing `open` counts as open; an `active` that isn't one of the area's tabs is its first. A tab whose session has gone is closed once the service's list of sessions has come in; a file or past session that can't be read shows its error in its tab.

**Moving in.** Before this, every client kept its tabs per feature in `localStorage`. The first time Sessions has no `layout.json` on a service, the app writes this browser's old Sessions tabs and panel state there, and stops keeping them in the browser. Projects' and Dialogues' old tabs were one layout for all their projects at once, so they are dropped rather than given to any one project; a project with no file starts with the defaults. A service without the layout route (older than the app) shows Sessions' old tabs but doesn't save changes to them.

## Header

From the left: the agentop icon, connection manager, the feature nav (and the update notices after it). At the right end: settings button, then the toggles of the left panel, the left area, the right area and the right panel. Nothing else goes in the header but the update notices ([design 7.4](0_00_design.md#74-releases-and-the-update-indicator)): a feature's New button (New dialogue) is the only thing in the Create new … section at the top of its left panel (Projects has none: its Project button is at the top of its Projects section; Sessions has none: it starts from the start buffer).

The four toggles are always there, in the same places, each with its pressed state (`aria-pressed`) showing whether its part shows:

- **Left panel**, **right panel** (Ctrl+Shift+1, Ctrl+Shift+0): disabled in a feature without that panel (Memory has no left panel) and while not connected. Kept as before: per project in its layout, per client in a feature without one.
- **Left area**, **right area**: hide an area of the middle panel, keeping its tabs, and show it again as it was; the other area then fills the middle panel and becomes the active one. Kept with the rest of the layout (`open` in [the format](#project-layouts)). Disabled for an area with no tabs, and for the only area shown, since the middle panel never shows neither. Opening, showing or focusing a tab there (Ctrl+Shift+W, E) shows a hidden area again. They have no keys of their own.
- Below 900px only one area shows: there the area toggles pick which, the one shown pressed and disabled. Below 600px the feature nav is a drop-down and the service's name is cut short, so the header still fits a phone.

### Connection manager

A menu of the saved services, then Connect to a service:

```
┌──────────────────────────────────┐
│ ● build-box                Status│
│ ● gpu-1  Not encrypted     Status│
│ ○ office-mini  Unreachable Status│
│ ──────────────────────────────── │
│       Connect to a service       │
└──────────────────────────────────┘
```

- Selecting a row switches at once ([design 3.2](0_00_design.md#32-connecting-to-services)). Rows show live reachability from `/health`, polled every 15s only while the menu is open.
- **Connect to a service**: URL (or a pasted `connect-info` string) and an optional name. Test runs the connection checks first. The form warns about unencrypted URLs and likely browser blocks.
- **Status**, on each row, opens a Status tab in the left area, switching to that service first.

### Settings and Status

- **Settings** (the gear) is the app's own, the same for every service: theme, terminal font size, and terminal drawing (`auto`, WebGL, DOM).
- **Status** belongs to a service, and is a tab: a name field (an alias kept only by this client), address, version and commit, uptime, tmux version, encryption, Stop, Restart and Update (enabled by what the service's manager can do, with an update's progress step by step), the signed-in clients, Forget (removes the service and its token from this client; never for the service that served the page), and the service's **Plugins**, each with its switch, state, any error, and its own settings section.

## Keys

All layout keys are Ctrl+Shift with a physical key (`event.code`, so they stay in place on any keyboard layout). The core takes them before the terminal or anything else in the page.

| Key | Does |
|-----|------|
| Ctrl+Shift+1 | Left panel toggle |
| Ctrl+Shift+2 | Connection manager: opens or closes its menu |
| Ctrl+Shift+3 to 8 | The first to sixth feature in the feature nav |
| Ctrl+Shift+9 | Settings |
| Ctrl+Shift+0 | Right panel toggle |
| Ctrl+Shift+Q | Focus the left panel, showing it if hidden |
| Ctrl+Shift+W | Focus the left area, showing it if hidden; nothing if there isn't one |
| Ctrl+Shift+E | Focus the right area, showing it if hidden; nothing if there isn't one |
| Ctrl+Shift+R | Focus the right panel, showing it if hidden |
| Ctrl+Shift+A, S, D, F, G, H, J, K | The first to eighth tab of the active area |
| Ctrl+Shift+M | Toggle the input bar |
| Ctrl+Shift+L | Close the active area's tab (a session's tab only: the session keeps running) |

A feature after the sixth, a tab after the eighth, and a panel the feature doesn't have get no key.

Everything inside a section or a buffer belongs to whoever draws it, the core or a plugin, and may have keys of its own, as long as they aren't the keys above. The terminal's: Ctrl+Shift+C copies the selection, Ctrl+Shift+/ searches its scrollback.

Some of these are browser shortcuts too (Ctrl+Shift+Q and W quit or close a window), but the page takes them first: in Chrome, Q, W, E, R and J all reach the app (checked 2026-11-19). Other browsers are unchecked.

## Rules for plugins

- A plugin's feature gives a label, optional left and right panels, a background, the views its tabs show, and optionally one of them as its pinned `home` tab. Nothing else in the layout is a plugin's.
- A feature whose tabs belong to a project says so (`projects: true`) and shows one with the core's `setProject(feature, name)`; the core then keeps its layout in that project's `layout.json`.
- An action that awaits before opening a tab (a load, a request) captures its view first with `ownerOf` (the service, the feature and the project it shows) and opens with `openTabIn(owner, …)`: the tab lands in that view, shown or not, and never switches what the owner has gone to meanwhile. One that touches the service's state, such as adding a session it was given, does so only while that service is still the one shown. The core never opens another project's session in Sessions.
- A panel's content is `Section`s (from `components/Section.tsx`), each with a title, also when there is only one.
- A plugin adds to a core feature only through the slots in `plugins/types.ts`: a section in Sessions' right panel (`rightPanel`), a badge in a session row, a piece below a terminal, a section in Status.
- Tabs are opened with the core's `openTab(content, area)`, never by editing a layout, so the rules in [Where tabs open](#where-tabs-open) hold everywhere.
- No new kind of part (another bar, a floating panel, a third area) until the core has one. Ask for it in the core first.
