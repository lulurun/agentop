# Architecture

## 1 Overview

agentop has two parts: the core, which detects and manages agent sessions and serves the app and its API, and plugins, which add features on top (Projects, Dialogues, Waiting for input, the File viewer, Memory, Email code, the Input bar). Why it is built this way is in [0_00_design.md](0_00_design.md).

```
 ┌──────────────┐   ┌───────────────────┐
 │   Web app    │   │  Tauri desktop    │     both show the ui/ build
 │  (browser)   │   │  wrapper          │     that the service serves
 └──────┬───────┘   └───┬───────────┬───┘
        │ HTTP + WS     │ HTTP + WS │ on a PC: starts `agentop serve`
        │               │           │ on open, SIGTERM on close
 ┌──────▼───────────────▼──┐  ┌─────▼──────────────┐
 │  agentop service        │◄─┤ systemd --user,    │
 │  127.0.0.1:9775         │  │ by hand, or the    │
 │                         │  │ desktop app        │
 │  REST /api/v2           │  └────────────────────┘
 │  WS   events, terminal  │
 │  static web app         │
 │  SessionStore, plugins  │
 │    ops / scanner /      │
 │    AgentCli / registry  │
 └──────┬──────────────────┘
        │ tmux new-session / attach-session
 ┌──────▼──────────────────┐        ┌─────────────────────┐
 │ user's tmux server      │◄───────┤ agentop CLI, plain  │
 │ agent sessions          │        │ `tmux attach`       │
 └─────────────────────────┘        └─────────────────────┘
```

### Technology choices

| Area | Choice | Why |
|------|--------|-----|
| Service | FastAPI + uvicorn | Pydantic models give an OpenAPI schema |
| UI | React 19, TypeScript, Vite | Mature ecosystem for a stateful three-pane app |
| API client | Generated by `openapi-typescript` | One contract; a drifted client fails at compile time |
| UI state | Zustand, fed by the events socket | Small; the server is the source of truth |
| Terminal | xterm.js 6 | [design 5.2](0_00_design.md#52-terminal-library-xtermjs-6) |
| Desktop | Tauri 2 | Uses the system webview |

### Core and plugins

Everything described here is the **core**: always loaded, never switched off. New service-side features are **plugins**, one folder each under `src/agentop/plugins/` (UI under `ui/src/plugins/`), loaded by the core plugin loader, `service/plugins.py` (`PluginHost`), which lists them at `/api/v2/plugins` and enables or disables them. A plugin can also add `agentop` commands, from a `cli.py` the CLI loads itself (`plugin_cli.py`), without the service; what both read from a plugin's `plugin.toml` is in `plugin_manifest.py`. A missing, failing, or disabled plugin only hides its own feature. Plugins hear about sessions through `SessionStore.add_listener`, which turns each refresh into `session.started`, `session.exited`, `session.closed`, and `scan` events. How plugins work is in [0_12_00_plugins.md](0_12_00_plugins.md). Dialogues (section 5 below) are a plugin, in `src/agentop/plugins/dialogue/`.

## 2 Agent layer

`agentclis/` is the one place for the differences between the agent tools. Each tool has one module there, with a subclass of `AgentCli`. The rest of agentop asks a tool's `AgentCli` (`get_agent(name)`) and never names a tool itself: a new tool is a new module, and a change in how a tool works is a change to its module only.

### 2.1 AgentCli (`agentclis/base.py`)

The interface, with the default for each thing that differs:

| What | Members |
|------|---------|
| Spotting its process | `matches(proc_name, cmdline)` |
| Being installed | `binary` (the program `launch_cmd` runs), `skills_dir()` (where agentop installs its skills for it, or None) |
| Launching and resuming | `launch_cmd`, `get_resume_cmd()`, `start_timeout`, `mouse`, `post_start_hook()`; `start_session()` and `resume_session()` hand these to `launcher.launch()` |
| Where its files are | `home` (the user's home unless one is given, as tests do): every path the tool reads is under it |
| Its own session ID, for History | `new_session_id()` and `start_cmd(id)`, for a tool that takes an ID at launch (Claude's `--session-id`); `session_id_after(pid, started)`, the ID from the tool's own records once the process is gone (Codex's log, Antigravity's CLI log) |
| Typing into it | `deliver(session, text)`, which every prompt goes through: it takes the pane out of copy mode, then calls `send_text(session, text)` (bracketed paste, then Enter; no Enter if the paste failed; Codex waits a moment before Enter), `idle_seconds` (how long the screen must stay still before a reply is finished), `boot_seconds` (how long a dialogue waits before its first prompt) |
| Saved sessions | `get_saved_sessions()`, `delete_session()` |
| What it's doing | `get_session_meta()`: session ID, AI title, token usage, bridge URL, from one read of the tool's files |
| One-shot prompts | `ask_cmd(system)`, `ask(prompt, system, cwd)`, `ask_model`: one prompt in, one answer out, no tools and no session saved; the Memory plugin's summaries. Claude (`claude --print`) and Codex (`codex exec`) have it |
| Its transcripts | `transcripts_root()` (the tool's own folder), `archive_files(root)` (what the Memory archive copies), `transcript_files(session_id, root)` (one session's files), `conversation_reader(path)` (how to read one as prompts and replies), `side_conversation(path)` (a subagent's, left out of History's message counts), `token_usage(path)` (the tokens one file records), `searchable(relative)` (whether it goes in the Memory search table) |

### 2.2 The tools

| File | Class | Differences |
|------|-------|-------------|
| `claude.py` | `ClaudeAgentCli` | Bracketed paste. Session ID by PID from `~/.claude/sessions/`; title and token usage from the session log in `~/.claude/projects/<slug>/`; accepts the trust prompt. Archives everything but Claude Code's `memory/` notes; only `<project>/<session>.jsonl` is searchable, not subagents or tool output |
| `codex.py` | `CodexAgentCli` | Thread by PID from `~/.codex/logs_2.sqlite`, title from `state_5.sqlite`, tokens from the rollout; pre-trusts the folder. Bracketed paste and a settle delay; `boot_seconds = 20`. Archives `sessions/` and `archived_sessions/`, `.jsonl.zst` included |
| `antigravity.py` | `AntigravityAgentCli` | Title from its CLI log; bracketed paste; `idle_seconds = 15`. Transcripts in `~/.gemini/antigravity-cli/brain/<id>/.system_generated/logs/transcript.jsonl`. Conversations from before the rename to Antigravity are only in its binary `conversations/` store, and are not read |

`agentclis/__init__.py` exports `AGENTS`, `get_agent(name)`, `names()` (the CLI's `--tool` choices), `DEFAULT`, the tool used when none is named, and `installed()`, the tools whose program is on the PATH of the user's login shell (where sessions are typed) or of the service.

### 2.3 Getting the host ready (`service/host.py`, `skills/`)

`agentop serve` calls `host.prepare()` before it listens. It finds the installed tools, and stops with an error when there are none. For each one with a `skills_dir()` (Claude Code and Codex) it installs or updates the skills that ship in `src/agentop/skills/`: each is copied with a `.agentop` marker file, and a copy with the marker is replaced when the skill changes. A folder or link of the user's own with the same name is left alone and logged; a broken link, such as one to where the repo used to keep the skills, is replaced. The installed tools' names go to `GET /api/v2/tools` (`installed`), and the New session dialog offers only those.

## 3 Actor layer

### 3.1 Actor (`actor.py`)

Generic tmux send/receive. Knows nothing about the dialogue protocol or the tool.

- `send(text)` — types text in with the tool's `AgentCli.deliver`. Each paste goes through a tmux buffer of its own, deleted after, so concurrent sends can't swap prompts. `send_text` uses bracketed paste (`Session.paste_text_bracketed()`, ESC[200~…ESC[201~), so multi-line prompts arrive intact: a plain tmux paste turns each line break into Enter, which submits (Claude Code too, for a short paste)
- `receive() -> str | None` — polls the screen until stable for `idle_seconds`, returns full scrollback

### 3.2 AgentInstance (`agent_instance.py`)

Wires one `AgentCli` and one `Actor` together for a single running process.

```python
AgentInstance(agent, tmux_session_name, role_name)
  .actor      # the Actor
  .stop()     # /exit → wait 3s → kill tmux session
  .send_command(text)
  .attach(stop_event)
```

`AgentInstance` is the object `ops.py` creates when starting, stopping, or sending to a session.

## 4 Session management

### 4.1 Scanner (`scanner.py`)

Stateless — reads live process state and tmux pane list on every call.

- `scan_processes()` — iterates psutil, matches against `AGENTS`
- `scan_tmux()` — calls `tmux list-panes`
- `map_process_to_tmux()` — matches a PID to its tmux session via ancestry
- `build_sessions()` — combines process + tmux + agent metadata into session dicts

### 4.1a Where agentop keeps its files (`paths.py`)

Everything agentop writes is under `~/.agentop` (`AGENTOP_HOME` moves it):

| Path | What |
|------|------|
| `config.toml` | Settings you edit |
| `service.json` | The service's name and service token, mode `0600` |
| `state/clients.json` | The signed-in clients, with a hash of each one's token, mode `0600` |
| `state/` | What agentop rewrites as it runs: the sessions lock, `plugins.json`, `update-status.json`, `update.pid` |
| `projects/{name}/` | Each project's folder ([0_13_projects.md](0_13_projects.md)), with agentop's record of it in `.project/`: `project.json` and the project's `sessions.json`. `default` is the Sessions feature's; each dialogue is one too |
| `logs/` | `serve.log` (a service started by hand), `update.log` |
| `plugins/{id}/` | Each plugin's own files: `store.json` from `api.store`, and anything else under `api.data_dir`. The Memory archive is `plugins/memory/` |

New kinds of files go in one of these folders, not at the top.

### 4.1b Transcripts as conversations (`conversation.py`, `transcripts.py`)

`transcripts.py` lists a session's transcript files, the ones its tool reports (`AgentCli.transcript_files`). When the tool has deleted them it looks in the archives enabled plugins offer (`api.offer_transcript_archive`; the Memory plugin's is one), which keep each tool's layout, so the same lookup works with the archive as its root. Each tool's `AgentCli.conversation_reader` reads one of those files as prompts and replies, with what every reader shares in `conversation.py`; the File viewer shows it and the Memory plugin's messages table is built from it. `transcript_stats` counts a past session's prompts, replies, tokens (`AgentCli.token_usage`) and bytes for History's right panel, and `read_conversation` gives its main conversation, oldest first across its files, for its tab (`GET /history/{id}/conversation`). A session's file routes (`/sessions/{id}/files`, `changes`, `memory`, `transcripts`, and the File viewer's) also take a past session's History ID (`Context.session_row`, `api.session`), so its right panel shows its Files as a live session's does.

### 4.2 Registry (`registry.py`)

One JSON file per project, `~/.agentop/projects/<project>/.project/sessions.json`, keyed by tmux session name, all under one lock (`state/sessions.lock`); `load()` merges them and gives each record its `project`, and a new record goes where `project` says. Tracks which sessions were started by agentop (managed) and stores user-set descriptions. A start records the agent's pid and start time, and the tool's session ID when it is known at launch; the store adds the ID and AI title once it sees them, so History (`history.py`) can list and resume it after it ends; ended records are kept for at least `history_window`. `ops.start(project=…, readonly=…, counted=…)` records the project and the starting plugin's flags before the agent starts. A `readonly` session, such as a dialogue's agent, has a terminal that is always read-only (section 6), and neither `agentop send` nor the input bar types into it (`ops.accepts_prompts`); one not `counted` takes no place in `max_active_sessions`. The file from before projects, `state/sessions.json`, is moved into `default` on first use (`sessions.json.migrated` is left), with `owner` becoming `readonly` and uncounted.

A write never saves over a registry it can't read: one that isn't valid JSON is moved aside to `sessions.json.corrupt-<time>` and the write fails once, so the next starts a new registry; a read error fails the write and leaves the file. `plugins.json` and Memory's `state.json` are moved aside the same way. All of them are written with `jsonfile.write_json_atomic` (fsync, then rename).

### 4.3 Ops (`ops.py`)

Business logic layer called by both the service and `agentop/cli.py`. It returns the typed results in `results.py` and raises `OpsError` (`StartFailed` for a start, with the tmux session kept to show the error) instead of returning error dicts:

| Function | What it does |
|----------|-------------|
| `get_sessions()` | Merge scanner output with registry |
| `start()` | Launch agent via `AgentCli.start_session()`, register |
| `stop()` | Create `AgentInstance`, call `.stop()` |
| `find_session()` | The one live session a name means, ignoring case and the `-<suffix>` (`deploy` is `Deploy-2953204`) |
| `send()` | Type a prompt into a managed session with its tool's `send_text` (`agentop send`) |
| `get_saved_sessions()` | Aggregate history from all agents |
| `resume_session()` | Resume via `AgentCli.resume_session()` |

## 5 Dialogues (a plugin)

See [0_12_02_dialogue.md](0_12_02_dialogue.md) for full detail. The plugin is `src/agentop/plugins/dialogue/`, and its UI is `ui/src/plugins/dialogue/`. With both folders deleted the core and its tests run as before.

| Module | Role |
|--------|------|
| `__init__.py` | `register(api)`: the routes under `/api/v2/plugins/dialogue/`, and stopping running dialogues when the plugin is turned off (`api.on_disable`) |
| `cli.py` | `agentop dialogue start / list / stop / remove`, loaded by the CLI through `register_cli` |
| `model.py` | `Dialogue` and `DialogueMeta` (persisted to `~/.agentop/projects/<name>/`, a project of the plugin's) |
| `orchestrator.py` | `DialogueOrchestrator` thread: the relay loop |
| `parser.py` | `ResponseParser`: extracts BEGIN/END blocks from scrollback |
| `status.py` | `DialogueStatus` and `ReceiveStatus` enums |
| `scenarios/` | TOML scenario files and reader |
| `ops.py` | `start_dialogue()`, `list_dialogues()`, `stop_dialogue()`, `stop_running()`, `remove_dialogue()` |
| `runner.py` | The orchestrator process, `python -m agentop.plugins.dialogue.runner <id>`, started by `ops.start_dialogue()` |

The orchestrator is its own process, not part of the service, so a dialogue keeps running when the service restarts, and `agentop dialogue start` works with no service. Its agents are ordinary managed sessions started through `ops.start`, and it drives them with the core's `AgentInstance` and `Actor`.

## 6 Web layer

`service/app.py` assembles the service: the `/api/v2` API (`service/routes.py`, with a router per area in `service/api/`: clients, admin, sessions, history, projects, sockets; each handler gets the `Context` as a FastAPI dependency), plugin routes under `/api/v2/plugins/<id>/`, and the built app (`service/webdist/`) at `/`. Requests to `/app/...`, where the app was until 2026-11-14, are redirected there with a relative address, so it also works behind a proxy's path prefix. Every `/api/v2` route except `/health` needs a client's token; the service token only signs a client in, at `POST /auth/clients` (`service/auth.py`, [0_06_security.md 1](0_06_security.md#1-rules)). `service/store.py` keeps the session list, refreshed by a background scan, and pushes changes over the events WebSocket. The terminal is a `tmux attach-session` bridged over a WebSocket PTY (`service/terminal.py`). With `readonly=true`, or for a `readonly` session, it attaches with `-f read-only,ignore-size`, drops what the client sends, and takes the window's size, which it tells the client in a `{"type": "size"}` frame; the terminal then scales its font to show the whole window.

## 7 UI layer

`ui/` is one React app for both clients. `ui/src/api/` is the client generated from the service's OpenAPI schema; `store.ts` (Zustand) holds each connection's state, fed by the events socket; `src/terminal/TerminalView.tsx` is the only code that imports xterm.

### Platform layer

`ui/src/platform/` is the only place the two shells differ (`web.ts`, `tauri.ts`):

```ts
interface Platform {
  kind: "web" | "desktop"
  loadConnections(), saveConnections(…)           // saved list; tokens in the keychain or localStorage
  defaultConnection(): Promise<Connection | null>  // the service that served the page
  loadActiveId(), saveActiveId(…)
  copyText(text: string): Promise<void>
  checkAppUpdate?(release)                         // desktop: agentop in place, or a new app (design 7.4)
  startService?()                                  // desktop: this computer's service (design 7.2)
  openUrl?(url)                                    // desktop: the release page, in the browser
}
```

Everything else is shared, and nothing outside this directory imports `@tauri-apps/*`.

### Middle-panel tabs

The layout, its names and its keys are in [0_10_ui.md](0_10_ui.md). The middle panel holds a left area and a right area of tabs (`ui/src/tabs.ts`, pure functions over a `Layout` of `left`, `right` and the active area, kept per connection and feature in `store.ts` and saved in `localStorage`; the older `{groups}` shape is read as left then right). A tab shows a buffer: a session's terminal, a file through the enabled `file-viewer` plugin, a past session, Status, or a plugin's view. Every tab is opened with `openTab(content, area, mode)`: from the left panel in the left area, from the right panel in the right area, from inside a buffer in its own area (`useArea()` in `Workbench.tsx`), the area made when it isn't there. A tab already open in either area is shown where it is, except with `also` (a row's "Open in the right area"). The active area's tab decides the session in the right panel; a past session's tab shows it there (Details, Transcript, Files) and its conversation as a chat in the buffer, with Resume and Delete in the buffer's bar. Closing a session closes its tabs. The layout keys are read in one capture-phase listener in `App.tsx` (`hotkeys.ts`), ahead of the terminal, which lets them through (`TerminalView.tsx`).

The right panel lists the working directory (Files: Changed and All) and, as a third tab named after the tool, the notes the agent tool keeps for the session's project, from `GET /api/v2/sessions/{id}/memory` (`AgentCli.memory_folder()`). Only Claude Code keeps them as files for each project: `~/.claude/projects/<folder>/memory/`, where `<folder>` is the one holding the session's log, or before the first log the one named after the working directory with every character other than a letter or digit made `-`. The rest of that folder is the project's logs, not shown. Codex keeps its memories for all projects together (`~/.codex/memories/` and a database) and antigravity as protobuf, so neither has the tab. The agent tool's own log files for the session are listed by `GET /api/v2/sessions/{id}/transcripts` (from `AgentCli.transcript_files()`), which the panel no longer shows. Only files in the working directory, the memory folder, or that list can be read, through the File viewer plugin's route. A file from the Changed list opens as its diff, from the plugin's `/diff` route (`files.git_diff`: `git diff HEAD` with no external diff or textconv, an untracked file as wholly added), drawn by `viewer/diff.ts`. The viewer draws a Markdown file in the browser (`ui/src/plugins/viewer/Markdown.tsx`, react-markdown with GitHub's extensions, its HTML cleaned by rehype-sanitize's GitHub list), loaded only when one is opened. The images it names come from the plugin's `/image` route as data, since an `<img>` can't carry the token, and a link to a file beside it opens that file in a tab (`viewer/paths.ts`).
