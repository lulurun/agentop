# Agentop Implementation Plan

This plan implements [design.md](design.md). It assumes the defaults in the design's section 15. Changing D1 or D4 changes Phases 1 and 6.

## 1 Overview

| Phase | Outcome | Needs | Size |
|-------|---------|-------|------|
| 0 | Security fix shipped; unknowns resolved | — | S |
| 1 | Service core with the `/api/v2` API | 0 | L |
| 2 | Web app: sessions, loading, terminal | 1 | L |
| 3 | Right panel: details, usage, files | 2 | M |
| 4 | Service control and update | 2 | M |
| 5 | Tauri desktop app | 2, 4 | M |
| 6 | Parity and cutover | 3, 4, 5 | M |

```
0 ──► 1 ──► 2 ──┬──► 3 ───────────┐
                └──► 4 ──► 5 ─────┴──► 6
```

Phases 3 and 4 can run in parallel. Sizes are relative: S is a day or less of focused work, M a few days, L about a week.

Rules for every phase:

- The current dashboard keeps working until Phase 6.
- Tests never touch the live tmux server; they use a private socket.
- Each phase ends in a state that can be merged and deployed.

## 9 Backlog

Work agreed but not started, and ideas not yet scheduled. It replaces `TODO.md` (removed 2026-11-15); what was done there is recorded in the design and in git history.

### 9.1 Security

The security review of design section 7 was finished on 2026-11-15: TLS required off loopback, per-client expiring tokens that can be revoked, a closed `/health`, open CORS and skip-permissions agents kept on purpose. One item is left, at lower priority, because it makes signing in less convenient, which matters little on a hardened host and a lot for personal use.

- [ ] Single-use pairing codes, so the service token never has to leave the machine. Discussed 2026-11-14, not built. For a phone, the Email code login plugin (design 7.4, 2026-11-16) now removes most of the need. Approving a new device from one already signed in would be another login plugin.
  - Today the service token never expires, and signing in a browser or phone means copying it off the machine (into a chat, a password manager, a phone). Each copy can leak, and whoever has it can sign in clients until it's rotated.
  - `agentop service pair` on the machine prints a short code, such as `K7QF-2M9X`. It is typed into the app's sign-in form instead of the service token, works once, and expires after 10 minutes, so a code that leaks later is useless. Making one needs shell access to the machine (SSH, or sitting at it).
  - A setting turns the service token off for `POST /api/v2/auth/clients` entirely, so pairing codes are the only way in. Without it the codes add little. It can't be "refuse it except from loopback": behind a proxy such as nginx on proxy-host, every request comes from `127.0.0.1`.
  - The CLI and the desktop app then sign in by writing a pairing code into `~/.agentop/state/` and using it, instead of sending the service token. Only something that can write to the user's home can do that, the same trust the `service.json` file gives today.
  - Downside: every new browser or phone, and every sign-in after 12 hours unused, needs a fresh code from a shell on the machine.

### 9.5 Desktop app installs its own agentop

Agreed 2026-11-18, not built. The desktop app stays a thin wrapper and the only release artifact (`desktop-v*`); nothing is added to `v*` releases. On first run it sets up its own copy of agentop, then starts, stops and updates that copy. For a PC (macOS first) with nothing installed beyond the runtimes.

- [ ] **Where things live.** `~/.agentop-desktop/` holds only the code: a git checkout of `main` and a venv. Sessions, Memory and config stay in `~/.agentop/`, shared with the CLI.
- [ ] **The setup screen.** An interactive page the app shows until every step passes. Each step shows ✓ or ✗, with a one-line fix and a Check again button. A step runs only once the ones before it pass:
  1. **Dependencies.** Python ≥ 3.13, Node ≥ 22 with npm, git, tmux. The app doesn't install them: Homebrew, pyenv, mise, nvm and the rest are the user's choice, and some need root. Each is found through the login shell (`$SHELL -ilc`), as the app finds `agentop` today, so version managers work. The agent tools (claude, codex, agy) are listed too, as a warning only.
  2. **Install.** `git clone` of `main` into `~/.agentop-desktop/agentop`, `python3 -m venv ~/.agentop-desktop/venv`, and `pip install` of the checkout into it. Progress goes to a log the screen can show.
  3. **`agentop` on PATH.** A link `~/.local/bin/agentop` → `~/.agentop-desktop/venv/bin/agentop`. On macOS `~/.local/bin` isn't on PATH by default: the screen says so and offers to add it to the shell's profile (`~/.zprofile` for zsh), showing the line it adds.
  4. **`agentop` reachable from both sides.** From the wrapper, through the login shell. From the agents, in a tmux pane started the way agentop starts sessions (the shell the agent tools inherit), so the `handoff` and `recall` skills can run `agentop send` and `agentop recall`. Both must resolve to the app's copy: another `agentop` earlier on PATH, such as a dev checkout, is reported, not silently used.
  5. **Build the UI.** `npm ci` and the build into `src/agentop/service/webdist/`, as `scripts/build-ui.sh` does.
  6. **All PASS.** A final message, then the app starts the service from the venv and opens it.
- [ ] **Starting.** The app runs `~/.agentop-desktop/venv/bin/agentop serve`, not whatever is first on PATH. If a service already answers on the port (one started by hand, or a systemd unit), the app uses it, as today, and the screen says which copy is running.
- [ ] **Updates.** The service's own Update (`agentop service update`: pull `main`, install, build, restart, and go back if the new version doesn't come up) already works for a git checkout started by `agentop serve`, so the app's copy updates that way. The app shell needs a new `desktop-v*` release only when the wrapper itself changes.
- Not decided: whether to also offer following `v*` tags instead of `main`, and whether the check from the agents' side should also ask each tool to run `agentop --version` (slow, and costs a model call).
